## 組み込みの順序

### A. 基盤単体

1. `file-watch-assistance.ts`へ基盤を新設し、時計・予約処理をテストで注入できる形にする。インポート・生成時のファイル操作・自動タイマー開始は持たせない。
2. 登録/解除/世代、巡回中・待機中・停止、例外の分離、内部configureによる設定変更とOFF→ONの競合を実装する。既定OFF/300秒・最小2秒を基盤の定数として共有する。
3. 必須の障害報告関数と任意の時計を受け、ホストの状態・ファイルI/O・通知サービスへ直接依存しないクラスにする。実行時のデフォルト時計も確認する。
4. 基盤の単体試験、型検査、コンパイル、書式と実装レビューを終える。登録順・完了後の待機・停止時の未完了I/O・タイマー上限超を含めて確認する。
5. 設計・計画・検証記録を更新して、この工程で区切る。このworktreeでの単体実装ではホスト生成・保存設定/画面・既存observerを変更しない。mainへの反映後は発行・コミットする。

既存監視は基盤へ接続していないため、そのまま動く。基盤単体の成功を、ファイル受信・Explorer性能・既存機能との結合の検証済みへ読み替えない。

### B1. 保存設定と画面・ホストからの接続

1. 基盤の共有定数を使い、`host.fileWatchAssistanceEnabled=false`、`host.fileWatchAssistanceIntervalSeconds=300`を通常設定へ登録する。間隔は有限数で2以上、小数可とする。
2. 一般ページの保存先選択・JSON・入力確定・検索・リセット・公開設定APIまで通す。設定値の確定前には基盤を変更しない。
3. `index.ts`が単一インスタンスを生成し、内部configureへ確定した実効値を渡す。内部failedを共通障害報告へ接続し、生の例外・パス・認証情報を通知へ出さない。
4. 既存タイマーの置換まで完了してから工程Bを完成とする。旧監視と共通監視の二重動作を完成品として発行しない。

### B2. 設定と名簿の監視を登録

1. `observeFile`へ基盤の明示的な依存を渡す。製品の各呼び出し元まで同じインスタンスを接続し、引数省略時だけ旧定期監視へ戻る分岐は作らない。
2. 100msの通知集約と180msの安定確認を、定期タイマーから独立させる。補助からのPromiseは安定確認の試行まで待つ。安定しない書込中の候補は未適用のままその試行を終了できるようにする。
3. watch/初期照合/補助確認は同じ対象の実行管理と世代を共用する。watchの新しい要求を、補助確認中だからという理由で破棄しない。後から届く無関係な要求まで無期限に同じPromiseへ含めない。
4. 60秒の定期statと固定5分の周期を廃止する。補助ONの各巡回で内容まで照合し、通知とメタデータの両方を取り逃した編集を検出する。
5. 監視読取ワーカー、原子的保存、直接reload、revision照合、復旧、`invalidate`と古い失敗の拒否を維持する。
6. SettingsStoreのshared/device、ページ提供元の名簿、共有アカウントグループへ接続する。グループの最終購読解除・ページサービス破棄・store.closeで登録を解放する。
7. watchの失敗を自動ONや短周期の再登録ループで補わない。既存の障害表示、初期照合、通知/明示操作に伴う再登録、ONの場合の次回補助確認へ接続する。

### B3. 登録画像の通常監視と補助確認を分離

1. `watch()`のタイマー作成と`scan()`の`this.timer && !this.watcher`依存を外す。開始処理でwatch接続→初期走査の順を確保する。
2. 画像一覧の補助確認を1件だけ登録し、`stop()`で解除する。ON/OFFのために原画像や表示用キャッシュを破棄しない。
3. 通常通知は対象ファイルの再確認を基本とし、ファイル名がない場合・親の到着・監視再接続時は対象フォルダーを走査する。通知のファイル名も安全な名前として検証する。
4. 走査中に届いた変更を記録し、必要な後続確認へまとめる。現在の`refreshing`をそのまま返すだけで後発の変更を失わないようにする。
5. 未作成rootの祖先watchと到着時の切替を実装し、補助OFFでも後から届く原画像を取得できるようにする。
6. メタデータ走査と原画像の遅延読込・decodeを分離したまま保つ。読込中の置換・削除・closeに対する世代検査を維持する。

### B4. 起動・設定反映・終了と旧データ確認

1. `index.ts`は基盤を1個だけ所有する。設定を監視する前からOFF状態で注入できるようにし、初期化が成功して対象の初期照合が揃った後に開始ゲートを開く。
2. 初期値と`settings.on('changed')`から2項目の実効値を反映する。同値のconfigureは待機を延ばさない。ページの保存先切替・reset・MCPによる変更も同じ反映経路を使う。
3. 後から開始する名簿等は所有者の初期化時に一度照合する。基盤へ登録したことを理由にViewや認証処理を生成しない。
4. LegacyLocalDataMonitor/inspectLegacyLocalDataと専用状態・文言・アクション・試験を削除する。起動時1回の確認も残さず、共通WarningReporterは保持する。
5. 終了処理はサービスのshutdown待ちより前に基盤の新規巡回を止める。各所有者の既存close/stopと遅い結果の拒否も維持する。起動中断・初期化失敗でも待機を残さない。
6. 通知音の2秒一覧確認は変更しない。その残存を検証記録と利用者への案内に明記する。

## 検証計画

永続試験は[テスト方針](testing.md)に従い、利用者の設定・保存・受信・停止を守る結果を検査する。タイマーの変数名やCSSの細部だけを固定する検査は作らない。

### 基盤の単体試験

[tests/file-watch-assistance.test.cjs](../tests/file-watch-assistance.test.cjs)へ、注入時計と完了を制御できる処理で集約する。工程Aで実行し、ネイティブ時計での実行と待機中のプロセス終了も確認する。以下の結合・固定EXE・性能試験は工程Bで行う。

| 契約                             | 確認する結果                                                                                                                        |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 登録順・直列                     | 先の処理のPromiseが終了するまで次が始まらず、補助処理の同時実行が最大1                                                              |
| 全件終了後の待機                 | 処理時間を含めて次の開始が後ろへずれ、遅れの埋め合わせをしない                                                                      |
| 既定OFF・開始ゲート・登録0件     | 初期照合とは別に、補助I/Oと不要な待機タイマーがない                                                                                 |
| OFF/ON・間隔変更                 | 待機中/実行中の両方、現在処理中の再ONでも二重巡回しない。補助確認で受信した設定が自身をOFFにした場合も残りを開始しない              |
| 同じ設定の再適用                 | 他の設定更新が続いても次回実行が先延ばしにならない                                                                                  |
| 登録の追加・解除・同じIDの再登録 | 巡回中の追加は次回から、解除済みは未実行、古い解除関数は新登録へ影響しない。全登録を解除してすぐ再登録しても、旧I/Oの終了後から待つ |
| 失敗と停止                       | 1件の失敗後も次へ進み、dispose後は次回実行・結果反映がない                                                                          |
| 長時間待機・入力値               | 2秒・小数・不正値・タイマー上限超の分割予約。分割満了がファイル確認を起こさない                                                     |
| 完了と取消の違い                 | 取消通知や待機打切りだけでは実行枠が空かず、実I/Oの未完了中に次を始めない                                                           |

### 固定EXEと実測

- 固定EXEを隔離profileで起動し、一般のフォーム/JSONからON/OFFと2秒/長い待機へ変更する。blur/Enter確定、Escape取消、不正値、再起動後の保持、ページリセット、共有/PC専用切替を確認する。既存の`scripts/device-settings-ui-test.cjs`・`scripts/settings-controls-ui-test.cjs`の関連経路を拡張して使う。
- 広幅/狭幅と明暗の代表画面を確認する。検索アンカー、OFF時の間隔欄、保存失敗時の入力保持、既存設定のフォーカスと保存を確認する。
- `scripts/settings-sync-ui-test.cjs`と`scripts/lazy-registered-images-ui-test.cjs`等の関連経路で、OFFでも通常通知が働くこと、後着画像の回復と不使用画像の非decodeを確認する。旧保存形式に依存するfixtureは、実行前に現行構成と照合する。
- 監視APIの欠落・失敗と時間進行はfixtureで再現し、実Windowsの通知確認と分けて記録する。実同期ソフトやNASでの結果をfixture成功から推定しない。
- 起動準備完了・初期照合完了を待ってから、対象別のstat/readdir/read/decode回数と巡回時刻を測定する。OFF時は初期化後の設定/名簿/画像の補助アクセスが0、ON時は全件完了後に待機時間が入ることを確認する。
- 対象0件・1件・多数、遅い処理、処理中の設定変更を測る。速度向上のための件数上限は追加しない。通知音の残存ポーリング・ログ追記・通常の利用時読取は対象別に分けて集計する。
- 実際のExplorerの操作感は別の実機確認項目とする。コード上のI/O削減だけでExplorerの遅延解消とは報告しない。

## 工程Bの完了条件と配布

1. 設計書の登録・完了待ち・OFF/ON・間隔変更・停止契約が実装されている。
2. 製品から作る基盤が1個で、設定/名簿/画像の独立した定期タイマーがなく、旧データ残存チェック機構が削除されている。
3. 補助OFFでも通常監視・初期照合・保存の競合確認が働き、最後の正常値・原画像・認証・他端末のデータを保持する。
4. 必要な単体/結合/固定GUIと計測が成功し、残る通知音ポーリング、未検証の実同期/NAS/Explorerを明示している。
5. 実装差分と影響先を1回レビューし、阻害指摘を解消して必要な再検証を終えている。
6. 設定項目を追加するため、実装を完成して発行する際は、その時点の版からマイナーを1つ増やしパッチを0にする。基盤単体の0.111.1から他の版更新がなければ0.112.0。設計だけでは版を変えない。
7. 実装依頼後は[共通手順](development-workflow.md)に従って本体をpublishし、固定成果物を確認する。未変更Appletを再発行しない。commit・push・Release・実利用先deployは別の依頼範囲に従う。

サウンドライブラリーでは、現在の一覧ポーリングを撤去して通常watch・初期照合・共通基盤への登録へ置換する。再生・通知キュー・登録素材の保存契約は別途設計し、この計画だけで実装を開始しない。
