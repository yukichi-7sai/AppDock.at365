# 共有settings.jsonとdataの保存先を端末ごとに指定する設計

状態: 未実装。現在の保存先・同期・復旧は[設定同期](settings-sync.md)を正本とし、以下は参照先変更を実装する場合の設計とする。

## 目的と決定

各PCの一般設定で共有settings.jsonの場所を選び、その隣のdata/も一緒に使う。複数PCがNASの同じ共有ルートを参照する場合は、設定値・登録素材・共有アカウント名簿を同じ場所から読み書きする。既存のファイル同期による受信・検証・反映の考え方を利用し、NAS向けに共有書き込みの排他と通信障害への対処を加える。

| 対象 | 決定 |
| --- | --- |
| 設定する画面 | 本体の「設定 → 一般 → 設定ファイル」 |
| 未指定時の共有設定 | 従来どおりEXE隣のsettings.json |
| 指定時の共有設定 | このPCで指定した既存のsettings.json。ローカル絶対パスとSMBのUNCパスに対応 |
| 参照先の指定の保存先 | EXE隣の自端末用settings-<端末名>.json。共有Settingsの値には含めない |
| 端末用JSON | 共有設定の場所から独立させ、EXE隣の固定パスを維持 |
| 切り替えの適用 | 選択した参照先を端末用JSONへ即時保存し、再起動後に適用 |
| 切り替え時の内容 | 切り替え先にある正常な設定を採用。元の設定のコピー・移動・上書きは行わない |
| data/ | 使用中のsettings.jsonの親/data。設定ファイルと登録素材・共有名簿を一緒に切り替える |
| 認証・許可・実行状態 | 従来の配置IDに対応するPC専用rootを維持 |
| NAS切断時 | 同じ参照先の最後の正常設定・取得済みの名簿や素材で可能な範囲を継続。共有への書き込みを止め、復帰時はNAS上の正常データを読み直す |
| 同時保存 | 同じ実ファイルを使う対応版AppDock間で、SMBサーバーが管理するファイルハンドルの排他を利用 |

設定ファイルの選択とdata/を一体で扱い、data/だけの独立したパス設定は設けない。既存ファイルの自動コピー・移動、ファイル同期サービスやNASの認証設定、設定の自動マージは追加しない。保存先の切り替えと、そこへ既存データを準備する操作を分ける。

## 現状と変更の必要な点

- `src/main/index.ts`は`baseDirectory/settings.json`をDeviceSettingsStoreへ渡す。共有設定を読む前に、参照先を端末用JSONから解決する入口が必要になる。
- `device-settings-store.ts`は共有ファイルの親から端末ファイルの場所を求めている。共有・端末それぞれの固定パスを別々に渡す構成に変更する。
- `device-settings.ts`の端末JSONはトップレベルとhostのキーを厳密に検証する。参照先のメタデータを明示的に定義し、設定合成と部分JSONの対象から分離する。
- `file-observer.ts`はwatchと2秒間隔のpoll、180msを隔てた同一内容の確認を行う。検証後だけ採用する契約を維持し、ネットワークの読み取りをmainの同期I/Oから外す。
- `settings.ts`の原子的置換は保存直前のbytes照合を持つが、照合とrenameの間に別プロセスが書く場合を排他していない。同じNASファイルを直接使う保存には、PC間の排他が必要になる。
- 現在の複数ファイルの回復記録は共有／端末というscopeを現在のパスへ解決する。参照先が変わった後に別ファイルへ復旧しないため、記録を共有参照先の識別子に結び付ける。
- GPU設定はapp.ready前に使用する。ネットワークからの設定読み込みを、この早期処理の必須条件にしない。
- `data-paths.ts`と`index.ts`からHost API・ページコレクションへ共有ルートを渡す。共通画像も注入されたassets rootを使う。共有場所切替ではRegisteredImagesを参照先別に作り直し、正常表示と生成キャッシュを別の共有先へ使い回さない。
- `web-profiles.ts`、`web-account-groups.ts`には共有名簿の同期I/Oと独自の回復処理がある。素材一覧・登録・音声読取も含め、共有設定だけを非同期化してNAS対応済みとは扱わない。

## 保存領域の分離

以下の値を別々に解決する。共有先を変更しても、EXEの配置IDを再計算する入力は変えない。

| 値 | 解決元 | 用途 |
| --- | --- | --- |
| 配置先 | 元のportable EXEの配置先。隔離試験は既存のprofile引数 | EXE、Applet、端末用JSON、更新対象、通知の起動先 |
| 共有設定ファイル | 自端末用JSONの任意メタデータ。未指定なら配置先/settings.json | 共有設定の読み書き・監視・復元 |
| 共有ルート／共有data | 共有設定ファイルの親／その下の小文字data | 登録素材、共有名簿、共有相対参照の解決 |
| PC専用root | 従来どおり配置先の正規化絶対パスから生成した配置ID | 認証、許可、session、Storage、Secrets、履歴、バックアップ、回復記録 |

構成例:

```text
D:/Apps/AppDock/
  AppDock.at365.exe
  settings-PC-A.json          このPCの設定と、共有設定の参照先
  settings.json               既定の共有設定。切り替えても保持
  data/                       切り替え前の共有データ。自動移動・削除せず保持
  extensions/

//NAS/Apps/AppDock/
  settings.json               指定した共有設定
  data/                       同じ共有先の登録素材・共有名簿
    assets/images/
    assets/applets/<Applet ID>/
    web-profiles/<Applet ID>/accounts.json
    web-account-groups/<group-id>/accounts.json
    web-applets/accounts.json
  settings.json.appdock-lock  対応版AppDockが保存時に使う恒久的な排他用ファイル

%LOCALAPPDATA%/at365/AppDock/profiles/<従来の配置ID>/
  settings-backups/
    last-good.json            既定参照先の従来のバックアップ
    shared/<参照先ID>/        指定した参照先の正常世代
    device/<端末キー>/        端末設定の正常世代・初期化済み記録
  settings-transactions/      設定保存の回復記録
  shared-cache/<参照先ID>/    取得済み名簿・検証済み素材のPC用キャッシュ
  ...                         従来の認証・許可・実行状態
```

### data/の扱い

選択したsettings.jsonの親を共有ルートとし、必ずその下のdata/を使う。`data/assets/...`のような共有相対参照は、この共有ルートを基準に解決する。設定値に保存する相対パス・ファイル名・UUIDは書き換えない。共有先を変えても、Appletが利用者に指定された任意の画像フォルダー等の絶対パスを置換しない。

| data内の対象 | 切り替え・保存の契約 |
| --- | --- |
| data/assets/images | 共通原画像。共有設定のimageLibrary.groupsと同じ参照先へ切替。元bytesと同名衝突の契約は[共通画像](registered-images.md) |
| data/assets/applets/<Applet ID> | 宣言済みの登録原素材。通知音は16MB以下のWAV・512件上限・同名別内容拒否を維持 |
| data/web-profiles、data/web-appletsの共有名簿 | 共有のUUID・表示名を参照。Cookie・session・削除待ち記録はPC専用のまま |
| data/web-account-groups/<group-id>/accounts.json | 共通名簿だけを共有。選択・監視・音の好み・旧session参照はPC専用のまま |
| 旧PC専用データ、未知のディレクトリー | 共有対象として走査・変更しない。既存の固定対象の警告と手動整理の契約を維持 |

切り替え先には、その設定に対応するdata/を利用者が準備する。選択画面では派生するdata/の場所も表示し、登録素材や名簿も切り替わることを明示する。切り替えのために旧・新どちらかのファイルを自動コピーしない。

data/がまだない場合、選択時や起動時に生成しない。設定にある素材・アカウント参照は不足／同期待ちとして保持し、EXE隣の旧data/へフォールバックしない。data/がディレクトリー以外、読取不能、不正な転送先である場合は選択の検証エラーとする。必要なフォルダーは、接続が正常なときの明示的な素材登録・名簿作成でのみ、許可された相対パス内へ作成する。

### PC専用領域との境界

認証・許可・Storage・Secrets・通知履歴・ページ位置・Chromiumは共有ルートから求めない。ログは[現行のログ仕様](logging.md#保存先と端末間の同期)に従い端末名で分けた共有dataへ記録し、書込失敗時の退避先だけを既存PC専用rootから求める。共有場所の切替時も既存ログを移行/再送しない。Cookieとsessionは従来の配置ID・Applet/グループID・アカウントUUIDの組に対応するPC用パスを継続する。共有名簿に同じUUIDがある場合は、そのPCの既存ログインを再利用できる。名前だけの一致で別UUIDのログインを結び付けない。

名簿の取得状態、未完了トランザクション、素材キャッシュは参照先IDへ結び付ける。切替元の名簿・pending・rosterKnownを切替先へ適用しない。sessionの保存場所は維持し、参照先ごとの取得状態はPC専用メタデータとして分離する。

## 端末用JSONの形式と参照先の検証

既存のDeviceSettingsへ、トップレベルの任意フィールド`sharedSettingsFile?: string`を追加する。schemaVersionは1を維持する。以下は追加するフィールドだけの抜粋であり、ファイル全体の例ではない。

```json
{
  "sharedSettingsFile": "\\\\NAS\\Apps\\AppDock\\settings.json"
}
```

- 未指定はフィールドの省略で表す。UIで空に戻した場合も省略する。空文字、null、相対パスを保存しない。
- 既存の端末用JSONはそのまま読める。新機能を使わない端末へ、このフィールドを自動追加しない。
- hostの既存8キーへ混ぜない。combineSettingsの返すSettings、AppletのsettingsChanged、部分JSON、生成設定コマンド、MCPのsettings.getへ渡さない。
- 通常の端末設定保存・バックアップ・復旧は、このメタデータも保持する。保存先の変更は専用の端末メタデータ操作で行い、Settings全体のsaveへ偽のhostキーを追加しない。
- ファイル名は大文字小文字を無視してsettings.jsonに限定する。端末用JSONやバックアップそのものを共有参照先に選べない。
- Windowsのドライブ付き絶対パスとUNCパスを受け付ける。URL、ドライブ相対パス、デバイス名前空間、代替データストリーム、制御文字を拒否する。環境変数やシェル構文を展開しない。
- ネットワークドライブ文字も絶対パスとして扱えるが、通常起動・管理者起動・サインイン時で接続状態が異なることを説明し、NASにはUNCパスを案内する。ドライブ割り当てや資格情報の登録は自動実行しない。
- 保存文字列はWindowsの絶対パスとして正規化し、画面用の大文字小文字は保持する。参照先IDは正規化パスを大文字小文字非依存で識別したSHA256とする。別名パスのバックアップを自動統合しない。
- 派生する共有dataとPC専用rootが同一・包含関係になる指定を拒否する。共有素材・名簿を認証や回復記録の領域に重ねない。隔離試験では既存の`--test-local-state`を使い、共有dataとは別のPC用rootを明示する。
- 選択時に通常ファイル・4MB以下・JSON/schemaの正常性を検証する。既存監視と同様に180msを隔てて同じbytesを確認する。派生するdata/の種類・到達状態も確認し、検証のために選択先・data/・親フォルダー・排他用ファイルを作成しない。全素材の再帰的読み込みを選択の前提にしない。
- リンクや別名を経由する場合も、共有ルート・実際の保存対象・排他用ファイルを一意に解決する。シンボリックリンクをrenameで通常ファイルへ置き換えない。data/配下の素材・名簿が登録root外へ転送される構成は既存の保護と同様に拒否する。解決対象が変わった場合は処理を中止し、排他の同一性を確認できない構成は共有保存を許可しない。既存の同期・リンクの設定自体は変更しない。

旧版は未知のトップレベルフィールドを拒否するため、この指定を保存した端末用JSONは旧版で読めない。ダウングレードする場合は対応版で「既定の場所に戻す」を実行し、再起動してから戻す。別PCの端末用JSONは読まないので、新機能を使っていない別PCのファイルを書き換える必要はない。

## 一般設定のUIと切り替え

既存の「設定ファイル」欄へ追加する。現在ページの設定JSONを開くツールバーと、設定基盤全体の診断という役割分担を維持する。

```text
共有設定とデータの場所
使用中: \\NAS\Apps\AppDock\settings.json
共有データ: \\NAS\Apps\AppDock\data
[変更…] [既定の場所に戻す]

この場所の指定は、このPCだけに保存します。
変更は再起動後に反映されます。
画像・通知音・共有名簿も、選んだ設定ファイルの隣のdataを使います。
既存ファイルのコピー・移動は行いません。

次回使用: D:\Shared\AppDock\settings.json    ← 変更後だけ表示
次回の共有データ: D:\Shared\AppDock\data
再起動して共有設定とデータの場所を切り替えてください。[再起動]
```

「変更…」は共通の設定ダイアログを使う。パス入力と「参照…」を提供し、参照ではsettings.jsonを選ぶ。入力中の文字列はダイアログ内だけに保持し、OKで登録単位に検証・即時保存する。全体保存ボタンや共有ドラフトは導入しない。

切り替え処理:

1. 既存の入力flushを通して、送信中・不完全入力・保存失敗を処理する。設定・素材・名簿の保存や復旧、アカウント削除、Windows起動設定、更新の処理中や、未解決の共有トランザクションがある場合は切り替えを開始しない。
2. 選択先を非同期で読み、パス・bytes・schemaを検証する。参照先の確認は読み取りだけとし、保存権限があることまでは確定したと扱わない。
3. このPCの設定のrevisionと変更前のメタデータを再照合し、参照先だけを端末用JSONへ保存する。別の入力が古い端末設定を丸ごと書き戻して指定を消さないようにする。
4. 使用中の参照先は切り替えず、「使用中」「次回使用」を別々に表示する。参照先変更用の再起動理由を既存の再起動通知へ追加する。
5. 次回使用と使用中が異なる間は、共有設定・素材登録・名簿変更と、それらを含む複数ファイルへの新たな書き込みを止める。画面に再起動の案内を出し、通常の共有編集を無言で捨てない。現在の共有先の読み取りと、独立した端末設定の編集は継続する。
6. 通常の再起動経路で終了し、次回起動時に選択先を再検証して、設定とdata/を同じ共有コンテキストとして採用する。ファイルを選択した時点の設定内容を、後からそのファイルへ書き戻さない。新しい名簿に不足があっても旧data/へ戻さない。

既定に戻す操作も同じ検証を通す。既定ファイルがなく正常な読み取りを確認できない場合は、設定ファイルを準備する案内を表示し、操作を保存しない。参照先を使用中の場所へ戻した場合は、再起動理由と共有保存の保留を解除する。

端末用JSONの外部変更で参照先が変わった場合も、動作中にホットスワップせず、同じ「次回使用」と再起動待ちへ移る。現在値と失敗した入力を同じ表示へ混ぜない。検索には「共有設定」「settings.json」「保存先」「NAS」を登録する。

## 起動順序と復旧用の入口

ネットワークへ接続できることを、端末設定の読み取りや復旧画面の表示条件にしない。

1. 配置先・OS端末名・従来のPC専用rootを確定し、自端末JSONの固定パスを求める。他端末のファイルを列挙・代用しない。
2. 自端末JSONまたはその端末用の正常世代を読み、GPU等の早期端末設定と共有参照先のメタデータを取得する。端末JSONが壊れている場合は、共有ファイルの場所を既定へ戻さず端末設定の復旧へ進む。
3. app.ready前にはネットワークの読み取りを待たない。正常な端末設定がまだない初回はGPUを安全側のOFFで起動する。初回取り込みで要求値が変わった場合は、既存の再起動通知へ接続する。
4. Electronの起動後に設定I/O用の補助プロセスを開始し、参照先に結び付いた未完了トランザクションと共有設定を非同期で照合する。通常のShell・Applet・自動管理者起動は、有効な合成設定または同じ参照先の正常世代が確定するまで開始しない。
5. 共有設定が正常なら端末設定と合成し、既存の変更通知・起動経路へ渡す。参照先が変わったことだけで、Appletの有効状態や端末専用設定を再初期化しない。
6. 自端末JSON・初期化済み記録・端末用バックアップが初めからない場合だけ、従来の初回初期化を行う。明示指定先が欠落・読取不能である状態を初回起動と扱って、既定設定を生成しない。

### 正常な共有設定を確保できない場合

起動前の復旧ダイアログへ「共有設定ファイルの場所を変更」を追加する。通常の設定画面を開けなくても、到達可能な正常ファイルを選び、自端末JSONへ保存して再起動できるようにする。「再読み込み」「保存先を開く」「終了」も維持する。

端末設定自体が壊れている場合は、先にその正常世代または正常な端末JSONを回復する。共有の復旧操作と端末JSONの復旧を混ぜず、共有設定を端末設定の代用品にしない。起動中の有効なUAC要求・Applet起動・コマンド実行を、復旧画面の副作用として発生させない。

## NAS読み書きの実行方式

mainからネットワークへの同期stat/read/write/renameを呼ばない。SettingsStoreと各名簿の検証・revision・採用判断を維持し、設定・名簿・素材・診断の共有I/Oを非同期のサービスへ分離する。

| 要素 | 責務 |
| --- | --- |
| 起動用の端末設定reader | 固定された自端末JSONと端末バックアップから、起動に必要な値と参照先を読む |
| SettingsCoordinator | 共有／端末の保存先分類、revision、操作の直列化、切り替え待ち、回復記録を管理 |
| SharedStorageIo | 操作IDと参照先の世代を付けた非同期要求、期限、補助プロセスの寿命、結果不明状態を管理 |
| 内部補助プロセスAppDock.SharedStorageHost | 登録済みの共有ルートと宣言済みの対象に限定した読み取り・排他・一時書き込み・置換・再照合を実行 |

補助プロセスは既存の.NET配布基盤を使って単一EXEへ同梱し、利用者に別の常駐サービスやRuntime導入を要求しない。非表示で起動し、親プロセスの終了・接続切断時に終了させる。パス、操作、対象ごとのサイズ上限を検証し、外部から任意ファイルを操作する汎用APIにしない。素材の16MB上限を設定JSONの4MB上限と混同しない。名簿は各現行schemaとサイズ上限を維持する。

既定のローカル共有設定にも同じ経路を使い、指定先がローカルかNASかで競合処理の正本を分けない。端末だけの通常保存は固定された端末ファイルを照合すればよく、共有ファイルを毎回読むことを前提にしない。

- 正常時のpollは現行の2秒間隔とし、watchを併用する。ネットワーク上ではwatchだけに依存しない。
- 同じファイルの読み取りを重複実行せず、poll・watchの通知をまとめる。共有先全体の要求数を制限し、素材の一覧監視・名簿・設定の処理を切断中に積み重ねない。
- 初期値は読み取り5秒、保存10秒、排他取得の待機2秒とする。障害継続中の再確認間隔は2、4、8、最大30秒へ延ばし、手動の再読み込みは即時に要求できる。正常復帰で2秒へ戻す。
- 期限を過ぎた要求は世代を無効化し、補助プロセスの終了処理へ進む。遅れて返った応答で、値・revision・正常状態を更新しない。
- 書き込み開始後の期限切れや応答消失は「保存結果を確認できない」とする。期限切れやプロセス終了だけを、未保存の証拠として扱わない。再接続後の再照合まで、同じ共有ルートへの次の書き込み・復元・参照先切り替えを保留する。
- 書き込み済みか不明な操作を、自動的に再実行・rollbackしない。確認待ちの入力は現在のUIに残し、toggle・コマンドを再送しない。

WindowsのI/O中断とSMB応答の時間はサーバーにも依存する。ここでの期限はUIが待ち続けないための期限であり、NAS側の処理中断が同時に完了したという保証にはしない。

### 排他の方式

共有settings.jsonと同じ実ディレクトリーの`settings.json.appdock-lock`を、SMBサーバー上の共通の排他対象として使う。設定・共有名簿・素材登録の書き込みは同じ排他へ統一する。補助プロセスが`OPEN_ALWAYS`相当・読み書きアクセス・`FileShare.None`で開き、保存または復旧の照合が終わるまでハンドルを保持する。

Coordinatorは共有を含む操作を1つのトランザクションとして補助プロセスへ登録し、同じ操作内の設定・名簿・素材の処理へ排他セッションを渡す。内側の保存処理が再び排他を取得して待ち続ける構造にしない。セッションは登録済みの参照先と操作IDに結び付け、ローカルUI・Applet・MCPへ公開しない。

- 排他用ファイルは初回の実保存時にだけ作成し、通常は残す。存在そのものをロック中の印としない。取得できるハンドルが排他の正本になる。
- ロック取得後にファイルをunlink／再作成しない。時刻・PID・端末名を理由に他PCのロックを削除せず、期限付きの独自リースや古いロックの横取りを追加しない。
- 排他取得失敗は保存を実行せず返す。プロセス内mutex、Windowsの名前付きmutex、Nodeのexclusive-createだけでPC間の排他を代用しない。
- 排他を維持できない、またはSMBのハンドルが失効したことを示すエラーがあれば処理を中止する。接続を張り直して同じ保存を継続しない。
- 対応対象はこの共有モードを実装するWindows AppDockと、必要な共有モード・置換を提供するSMB共有とする。各NASでの実測は別途必要であり、満たせない場合に排他なしで保存する代替経路は作らない。

この方式で直列化するのは、共有ハンドルが正常に維持されている間の対応版からの書き込みである。接続喪失をまたぐ分散トランザクションの保証として扱わない。切断・保存結果不明の場合は新たな書き込みを止め、再接続後の照合へ進む。

### 設定ファイルの保存

1. 操作をプロセス内で直列化し、入力・revision・使用中の参照先ID・保存モードを確定する。dryRunとno-opはファイルを変更せず、排他用ファイルも生成しない。
2. 共有の排他を取得してからファイルを読み直す。読み取り可能な正常JSONであることと、編集対象のbefore・現在値・revisionを照合する。他PCの更新があれば採用し、古い操作を競合として返す。
3. 固有名の一時ファイルを共有設定と同じディレクトリーへ書き、検証済みのafter bytesを確定する。一時ファイルの別名衝突で既存ファイルを上書きしない。
4. 置換直前にも対象bytesを照合し、同じ保存操作の一時ファイルを使って置換する。既存の一時的なWindows置換拒否の再試行は、置換未実施が確定している場合だけ同じ操作の中で行う。
5. 保存先を再読してafter bytesとの一致を確認し、結果を返す。Coordinatorが回復記録・正常世代と合成値を確定してから、保存完了と変更を1回だけ通知する。
6. 排他を解放する。他の更新を上書きしない条件で、この操作の一時ファイルだけを回収する。

共有を含む一括保存・JSON復元・バックアップ復元・rollbackも同じ排他へ接続する。検証から置換だけ別の排他へ分割せず、必要な照合が終わるまで保持する。NAS上での置換・応答消失・プロセス終了は、故障注入と実SMBで確認する。

### 名簿と素材の保存

名簿は排他取得後に対象のbefore bytesと版、UUID、現在値、ローカル操作を再検証して保存する。共有ファイルへの全書き込みを同じI/O経路へ接続し、未着・破損・読取不能時に空の名簿や別の参照先の名簿で上書きしない。

素材登録では、読み取り・形式検証を済ませた後、共通排他内で一覧・件数・大文字小文字を無視した同名を再確認する。同名同内容は再利用し、同名別内容は拒否する。新しい素材は同じ登録ディレクトリー内の固有一時ファイルへ完成したbytesを書き、最終名が存在しないことを排他下で確認してから公開する。受信側は未完成の一時ファイルを一覧・再生対象にしない。

素材と設定を連動して保存する場合は素材を先に公開し、設定を後で保存する。設定保存が失敗しても登録原素材を自動削除しないという現行契約を維持する。後から別PCが参照し始めた素材をrollbackで削除しない。素材がまだ届かない場合は同期待ちを表示し、到着後に回復する。

この排他は同じ実ファイルと排他契約を使うAppDock間の保護である。手動エディター・旧版・ファイル同期ソフトは契約に参加しないため、既存のbefore bytes照合も残す。外部更新の自動三方向マージや履歴からの統合は追加しない。

ファイル同期で別々のローカルコピーを使う従来方式では、ロックのハンドルも各PCのローカルファイルに対するものになる。同期されたロックファイルがPC間排他を提供すると説明せず、受信した正常ファイルを優先する従来契約を維持する。

## トランザクションと参照先の固定

共有と端末を同時に変更する既存操作は、回復可能なトランザクションを維持する。2ファイルや複数PCをまたいだ原子性を前提にしない。

- 新しい設定journalは版2とし、使用中の共有参照先IDを記録する。復旧時の実パスは、検証済みの使用中の参照先と固定された端末パスからだけ解決する。journal内の任意パスを保存先として実行しない。
- 名簿専用pending、グループ名簿の復旧状態、Webプロフィールの削除待ちを参照先IDへ結び付け、対応する参照先でだけ回復する。参照先を確認できない記録は切替先へ再生しない。
- 共有の排他を保持してbefore/afterの照合、順次保存、committedの永続化、必要なrollbackを行う。rollbackは現在bytesがこの操作のafterに一致するものだけを対象とする。
- 参照先のメタデータ変更は通常の共有データ編集と混在させない。進行中・結果不明・未復旧の操作を先に解決し、変更の保存後は再起動まで共有設定・素材・名簿の書き込みを保留する。これにより、次回参照先を保存した後に旧参照先用journalを新たに作らない。
- 外部からの端末JSON変更等により、journalの参照先IDと起動時の指定が異なる場合は自動復旧を止める。「元の参照先を選んで復旧」を案内し、選択・検証したパスのIDが一致したときだけ処理する。この選択は元の処理を回復するための一時的な対象登録であり、未解決のjournalを残したまま次回使用の指定を書き換える操作にはしない。新しい指定先へ古いrollbackを実行しない。
- 従来の版1journalは、既定の共有設定と固定端末JSONに限って既存手順で回復する。未解決の版1journalがある状態でカスタム参照先を適用しない。
- Windows起動設定は常に端末保存であり、NAS到達不能だけを理由にこのPCの正常な設定変更を止めない。OS登録、UAC取消、既存のlaunch用journalの契約は維持する。

### 参照先ごとの正常世代

既定参照先は従来のsettings-backups/last-good.jsonと直近20世代を継続する。カスタム参照先はsettings-backups/shared/<参照先ID>/に同じ構成で分離する。端末用の正常世代と初期化済み記録は従来の場所を維持する。

復旧は、使用中と同じ参照先IDの検証済み世代だけを候補にする。別のNAS・既定ファイル・以前の参照先の設定を、到達不能な指定先の代わりに自動採用しない。同じパスでもファイル内容が変われば、届いた正常内容を優先する。

参照先を選択した時の検証済みbytesは、次回使用の参照先IDへ正常世代として保存してよい。これはローカルキャッシュであり、起動時には必ず指定先を先に確認する。キャッシュ確保に失敗した場合は別のバックアップ障害として表示し、NASが読めることとオフライン起動できることを同一視しない。

### 名簿・素材のキャッシュと機能ごとの継続

検証済みの名簿と取得済み素材は、PC専用rootのshared-cache/<参照先ID>/へ保存する。キャッシュを共有の正本やオフライン編集用の送信待ちとして使わない。名簿は対象ごとのschema・サイズ制限で検証し、受信順が異なる設定と名簿を勝手に整合させて書き戻さない。

アバターのURL生成、音声再生、登録済み素材の一覧、共通ログイン画面への投影は取得済みのモデル／検証済みローカルキャッシュから行う。snapshotやプロトコル要求のたびにNASへ同期アクセスしない。素材のキャッシュは参照先別・内容hash別とし、再取得できる未使用素材だけをLRUで整理する。容量の目安の初期値は同じPC専用rootの全参照先で合計128MiB、再生・表示中のものは回収しない。設定の正常世代・名簿・未完了の回復記録は、この素材用の容量整理で消さない。

- NAS切断中でも、同じ参照先から取得済みのアバターや通知音は既存の表示・共通再生APIから利用できる。未取得の素材は不足として扱い、別の共有先の同名素材で代用しない。
- 取得済み名簿とローカルsessionが揃っていれば、そのアカウントの通常表示・監視は継続できる。外部Webサービス自体の通信可否とは分ける。
- 名簿を一度も取得できていなければ、その名簿を必要とする機能だけを同期待ちにする。正常な共有設定を取得できている他の機能まで停止しない。
- 共有障害中はアカウントの追加・改名・共有名簿からの削除を保留する。PC用の選択・監視・音の変更等は、同じ参照先の正常な名簿と対象UUIDが確定しており、共有書き込みを伴わない場合だけ許可する。
- 接続復帰でアカウント枠が名簿から消えても、Cookie・sessionの物理削除を予約しない。物理削除は既存の明示操作とPC専用の削除待ちに限定し、対象の参照先・UUID・現在の参照・起動中Viewを再照合する。

| 状態 | 動作・保存・回復 |
| --- | --- |
| 正常な共有設定を読み取れた | 検証後に採用し、値が変わった場合だけruntimeへ通知。共有原データの更新では共通revisionを進める |
| 起動中に共有ファイルが欠落・破損・読取不能 | 直近正常値を維持し、共有への保存と共有を必要とする操作を止める。既定ファイルを代わりに生成しない |
| data/の一部だけが欠落・読取不能 | 対象の素材・名簿を不足／同期待ちにし、取得済みの同じ参照先の値を保持。正常な設定・別素材を巻き戻さない |
| 起動時にNASが読めず、同じ参照先の正常世代がある | その世代で継続し、オフライン／正常世代使用中を表示。共有保存は保留 |
| 起動時にNASも対応する正常世代も読めない | 通常のShell・Applet開始前に復旧画面。場所の変更・再読み込み・終了を提供 |
| 共有障害中の端末だけの編集 | 正常な自端末ファイルと期待revisionを照合して許可。共有値のコピー・共有へ戻る操作・混在編集は保留 |
| 保存先が読み取り専用・排他を取れない | 読み取りと適用は継続できる。保存は失敗を明示し、入力を現在のUIへ保持 |
| 書き込み後の応答消失 | 保存結果不明として次の保存を止め、journalと操作IDを保持。再接続後に排他下でbefore/after/外部値を照合 |
| 通信復帰・正常な設定や名簿の到着 | NAS上の正常データを採用。古いキャッシュや失敗したUI入力を自動送信しない |
| 失敗した入力の再適用 | 最新値と競合を確認した後、利用者の明示操作で行う。保存先やモードが変わっていたら再入力を案内 |

正常な受信で読込障害を解消しても、保存・バックアップ・反映・結果不明の障害まで一括で消さない。エラーと再起動理由は既存のSettingsHealthへ接続し、独自の通知種類や通知履歴を追加しない。

バックアップ復元は現在の参照先への書き込みになる。対象パスをローカルの確認画面で示し、他PCにも内容が反映されることを説明する。復元確認後にNASへ正常設定が到着した場合は、その値を採用して復元を中止する。

## API・設定画面・情報の公開範囲

- 参照先の変更は初回実装では本体のローカル設定UI専用とする。Applet、MCP、カスタムコマンド、外部起動引数へ任意パスの変更機能を追加しない。
- 保存メタデータは一般ページのauxiliaryへ、使用中／次回使用／状態という許可された情報だけを渡す。部分JSONや共有設定値へ混ぜない。
- 通常のGUI、部分JSON、Node/.NETの自己設定、生成コマンド、MCPの設定操作は、使用中のSettingsCoordinatorへ接続する。expectedRevision、dryRun、公開項目、非公開キー、capability、再入防止を維持する。
- I/Oの非同期化により保存完了がPromiseになる呼び出し元を洗い出す。GUIへの成功表示、MCP応答、AppletへのsettingsChanged、Windows操作の確定を、I/Oの受付時点で返さない。
- 画像・通知音・名簿のHost APIは同じ共有コンテキストへ接続する。AppletへNASの生パスを新規公開せず、素材の取得・共通再生・Webアカウントの既存APIを維持する。読み取りのためにフォルダーを作成する既存経路も分離する。
- パス・NAS名・生JSON・認証情報を、通知本文・履歴・読み上げ・MCP応答へ追加しない。フルパスはローカル設定画面、復旧ダイアログ、既存の診断ログの範囲に限定する。
- 共有設定ファイルの「ファイルを開く」「保存先を開く」と対象別の復元は、使用中の実パスを指す。端末設定のボタンはEXE隣の自端末JSONを開く。「次回使用」の確認用リンクは別に表示し、使用中と取り違えない。

## 導入・互換性

1. 利用者が元と先の共有ファイルへの書き込みを停止し、必要なsettings.jsonと対応するdata/の共有素材・名簿を同じ親フォルダーに準備する。UUID・相対構成を維持する。古いdata/にPC専用のstorage・secrets・session等がある場合は、共有対象として一括コピーせず現行の保存分類を確認する。
2. 各PCの一般設定で、その同じファイルを選択して再起動する。新規PCではそのPCの端末設定を作り、Appletの有効化と端末保存モードを既存仕様に従って選ぶ。
3. 設定・素材・共有名簿はNASの同じ実体を参照する。新しいPCのCookie・APIキー・操作許可はそのPCで準備する。NASの名簿だけでログイン済みと扱わない。
4. 同じ共有ルートへ書き込むPCは対応版を揃える。旧版や手動編集との競合は、共有排他による保証の対象外として案内する。NAS直接共有へ切り替えた対象に別の同期機構も書き込む場合は、その競合をAppDockの排他だけで防げると扱わない。

共有Settingsのschemaと既存の保存値は変更しない。参照先が未指定の既存配置は、そのまま従来のsettings.jsonを使用する。過去の端末JSON、共有設定、data/、正常世代を自動変更しない。

publish・deploy・自己更新・スターターの処理対象は従来のEXE配置先を維持する。NAS上のsettings.json・data/・排他用ファイルと、EXE隣の端末JSON・旧data/を配布生成物に含めたり、EXEと一緒に上書き・削除したりしない。参照先変更だけで、配置ID、通知の起動先、Windows起動タスク、更新先を作り直さない。

| `src/main/core/data-paths.ts`、`registered-images.ts`、`image-library-host.ts`、`registered-sounds.ts` | 共有assetsの解決、原画像・グループと音声の保護、非同期一覧・登録、参照先別の取得状態 |
| `web-profiles.ts`、`web-account-groups.ts`、`web-accounts.ts`、`page-collections.ts`、`host-api.ts` | 共有名簿I/O、共通排他、参照先別の取得状態・pending、既存データの保護、PC専用session維持 |
| `src/main/index.ts`、`settings-recovery.ts` | 早期端末読込と非同期共有読込の分離、起動前の場所変更、起動・再起動・更新との調停 |
| `settings-health.ts`、`settings-health-notifications.ts` | 場所変更による再起動理由、参照先別の障害、結果不明状態 |
| `settings-page.ts`、`settings-page-host.ts`、`settings-catalog.ts`、`src/shared/settings-page.ts` | ローカルUI用の投影・アクション・検索。共有Settingsへパスを出さない |
| `src/renderer/settings/SettingsForm.tsx`と共通設定ダイアログ | 使用中／次回使用の表示、ファイル選択、検証失敗保持、保存先を開く操作との一致 |
| 設定の保存呼び出し元 | SettingsCommands、SettingsInputSession、AppletManagement、Host API、ページコレクション、素材登録、WindowsLaunch等の完了待ちと失敗経路 |
| `legacy-local-data.ts`、診断と配布・検証スクリプト | 許可された共有対象だけの非同期診断、補助プロセスの梱包、固定EXE試験、NASを実利用先と誤認しない隔離パス |

実装は次の順に行う。

1. パス解決、端末メタデータ、参照先IDと正常世代の分離を追加する。未指定の既存JSONを変更せず、共有設定・共有data・端末のパスを分離する。
2. 補助プロセスと非同期I/O、ハンドル排他、期限切れ・結果不明・journalの照合を実装する。設定・素材・名簿の通常保存と復旧を同じ経路へ接続する。
3. mainの起動順序と保存呼び出し元を接続し、共有障害中の端末保存、名簿・素材のキャッシュ、GPU・Windows起動の契約を維持する。
4. 一般設定と起動前の復旧UIへ参照先選択を追加する。設定とdata/の切り替え待ち・再起動・ファイルを開く対象を揃える。
5. 必要な検証・差分レビュー・修正を行い、現行文書を更新して通常publishへ進む。設定項目・保存仕様・内部配布物が増えるため、本体は[共通手順](development-workflow.md#版更新の判断)に従ってマイナー更新する。具体版は実装着手時に決める。

今回の設計書作成では実装・版更新・publishを行わない。未変更Appletの版更新や再発行も実装の前提にしない。共通の公開APIに変更が必要と判明した場合だけ、その契約と最低ホスト版を別途整合させる。

## 検証計画と完了条件

| 分類 | 必須の確認 |
| --- | --- |
| 既存互換 | フィールド省略の端末JSON、既定パス、従来backup、端末用初期化済み記録、共有bytes不変、未知の保存値の保持 |
| パス | ローカル、UNC、空白・日本語・大文字小文字、相対・URL・デバイス・ADS拒否、端末JSON誤選択、リンク解決とリンク保持、別名の排他一致 |
| 保存境界 | 設定とdata/が同じ共有ルートへ切り替わり、相対参照・UUIDを保持。端末JSON・配置ID・認証・session・許可・更新先は元の配置を使う |
| 素材・名簿 | 切り替え先の画像・通知音・グループ／Webプロフィール名簿が使われ、旧data/へ戻らない。欠落・遅延・不正JSON・異なるUUID・同名別内容・件数上限・一時ファイル非表示 |
| 起動 | 既定／指定先の正常起動、初回GPU、NAS遅延で復旧UIを妨げないこと、端末JSON破損、指定先欠落を初回生成しないこと |
| 切り替え | 正常ファイル選択、検証失敗・取消・不完全入力、使用中／次回使用、再起動後の採用、既定に戻す、他操作・外部変更との競合 |
| 保存完了 | GUI・部分JSON・MCP・Node/.NET自己設定がI/O完了を待つ。dryRun/no-opで共有・端末・lock・OS・素材へ変更しない |
| 同時保存 | 2プロセスと2台のPCが同じSMB上の設定・名簿を編集し、排他後の再取得で古い操作を拒否。素材の同名同内容／別内容・大文字小文字・上限直前の同時登録も確認 |
| 排他の寿命 | 通常解放、親終了、補助プロセス異常終了、SMB切断・復帰、排他ファイルの残存、横取りなし。非対応時に排他なし保存へ進まない |
| 保存途中の故障 | 一時書き込み、置換直前・直後、応答前、committed前後で停止・切断。結果不明を即時失敗と誤認せず、再送・古い応答・無条件rollbackを防ぐ |
| 複数ファイル復旧 | 版1/2journal、各置換境界、外部更新、参照先ID不一致、切り替え待ち後の共有保存停止、旧参照先の選び直し |
| オフライン | 同じ参照先の正常世代・名簿・素材だけで継続、別参照先のbackup／同名素材非採用、未取得の機能だけ同期待ち、端末だけの保存、復帰時のNAS優先と失敗入力の非送信 |
| PC固有の状態 | 同じUUIDのsession・監視・音の好みを保持。別UUIDを名前で結び付けない。旧名簿pending・rosterKnown・Cookie削除待ちが新しい共有先に作用しない |
| 設定画面 | 本体設定、フォーム／JSON、検索、狭幅・テーマ・キーボード、使用中のファイルを開く、参照先変更の再起動通知、起動前の場所変更 |
| Windows起動 | 端末のGPU要求、通常／管理者起動でのUNCアクセス差、サインイン時のNAS遅延、UAC取消、タスク・launch journal・再起動経路の維持 |
| 配布 | 固定単一EXEへの補助プロセス収録、更新・再起動後の保持、別配置の分離、NASの設定・data/・lockとローカルの端末設定・旧data/を配布が変更しない |

最初に関連するsettings-sync/settings-editing/device-settings/settings-recovery/settings-page/settings-commands/windows-launch、registered-sounds、web-profiles/web-account-groups、Node/.NET Webアカウントと更新・素材の回帰を選ぶ。純粋関数、故障注入付きの実ファイル、2プロセスの排他、固定EXEの隔離GUI、実際の2台＋SMB共有を区別する。NASを使わないfixtureの成功から、特定NAS・実ネットワーク切断・実サインイン・実UAC承認の成功を推定しない。

実装前に製品回帰を実行して、この新機能の成功とは記録しない。実装・レビュー・publish時の実行結果と未確認事項は[検証記録](../VERIFICATION.md)へ残す。
