# 容量・分割処理・設定検索

## 今後の実装方針

システム上必須ではないのに、利用者の使い方や登録量を制限する目的で件数制限・容量制限を組み込まない。この方針は設定一覧に限らず、今後の実装全般に適用する。メモリー・保存容量・処理時間の負担を受け入れるかは利用者が判断する。

「通常はこれで十分」「多すぎる使い方を防ぐ」「実装を簡単にする」といった理由だけで上限を設けない。大量データに対する性能は、共通索引、遅延読み込み、ページ分割、分割処理などで改善する。表示や処理を分割する場合も、保存できる総件数や総容量の制限へ置き換えない。

上限がシステム上必須の場合は、OS・プロトコル・データ整合性などの具体的な根拠、制限する対象、必要な値を設計とレビューへ記録し、必要な範囲に限定する。通信・操作バッチ・実行キュー・AppletのSchemaであることだけを、制限を追加する根拠にしない。

## 通信・本文・ファイルの容量

AppDock独自の固定容量・本文文字数上限を設けない。CPU・メモリーの負荷を抑えることは、利用者が扱える総量を制限する根拠にしない。接続先・OS・規格に必須条件がある場合は、その一次資料・対象・値・超過時の動作を記録し、該当する接続先や形式の検証に限定する。

MCPサーバー受信、外部MCP中継の引数・結果・ツール一覧・Schema・HTTP/stdio通信、Applet JSON-RPC、共通設定API、カスタムコマンドの定義・Schema・結果、Storageの各scope、動的ページcontext、ページアクション、Webhook、プロセス起動用の内部通信に固定容量上限はない。本文が大きいことだけを理由に拒否・切り捨て・途中適用しない。MCP SDKのstdio既定バッファ上限も無制限へ明示的に設定する。

文章生成の入力・プロンプト・結果・応答、TTS本文・受信音声・推定展開容量・モデル/ボイス一覧、Webアカウントのreport・observer結果・画像・スクリプト、画像正規化、ローカルページ画像、内部Base64取り込み、設定一覧の画像取り込み、アイコン取り込み、Secretsの値に独自の容量上限を設けない。通常文字列設定の既定1万文字上限と通知タイトル・本文の固定文字数上限も設けない。Applet/接続先が明示するSchemaの意味上の条件は維持する。

設定の保存・外部変更監視、MCP関連保存ファイル、更新メタデータ・配布物・展開後ファイルにも固定容量上限はない。監視読取はワーカー内でファイルハンドルを回収し、読取前後の同一性・安定化・世代検査を維持する。更新物は分割受信してディスクへ保存しながらハッシュと実サイズを算出し、宣言値との一致を確認してから展開・適用する。パス包含、リンク・重複パス拒否、所有ファイルの保護、原子的保存・更新・復旧を維持する。

### 残す制約と分割単位

| 対象 | 根拠と扱い |
| --- | --- |
| OpenAI Imagesの参照画像 | [Images edits仕様](https://developers.openai.com/api/reference/python/resources/images/methods/edit)の1枚50MB未満（50,000,000 bytes未満）・最大16枚・対応形式をOpenAI向け検証で適用する。ライブラリー自体の容量上限にしない |
| OpenAI Imagesの生成条件 | 同仕様のプロンプト32,000文字、枚数1～10など、選択したモデル/接続先の条件をアダプターで検証する。別プロバイダーへ一律継承しない |
| 文章生成の出力トークン | 利用者が接続設定/APIで指定する生成条件として維持する。固定本文文字数上限を重ねない |
| Windowsのプロセス起動 | [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)の終端NUL込み32,767 UTF-16コード単位、[cmd.exe](https://learn.microsoft.com/en-us/troubleshoot/windows-client/shell-experience/command-line-string-limitation)の8,191文字を起動時に検証する。内部通信や保存値の上限へ流用しない |
| JSON・画像・音声・ZIP等の形式 | 有限の数値、型、循環参照禁止、対応形式とコンテナーの整合性を検証する。OS・ランタイム・codecが実際に扱える範囲を超えた失敗は明示する |
| 通信の読み書き | Node RPC送信64KiB、.NET RPC書込32Ki UTF-16コード単位、音声/画像の読取64KiB、内部生成画像取得256KiB、Webアカウント転送512KiB等は処理単位として維持する。全体容量や分割回数を制限しない |
| ページ分割・キャッシュ | 一覧のページサイズや再生成できるメモリーキャッシュの予算は全体を拒否する容量上限にしない。次ページ・再読込で全内容を扱えることを保つ |

ストリームのフレーミング、UTF-8、要求順序、書込完了・受領確認・取消・切断の契約を維持する。独自の分割形式をMCPの相手へ要求しない。JSON検証の固定要素数・段数を容量上限の代用にせず、循環や未対応Schemaはそれぞれの理由で拒否する。

入力欄と共通設定APIも保存先と同じ容量契約にする。カスタムコマンドの表示名・説明・カテゴリ、プロセス起動本文、MCP接続先の表示情報・引数・認証値、AI/TTS接続情報に独自の文字数上限を重ねない。Appletが宣言するminLength/maxLengthは非負の安全な整数とし、AppDock側の最大1万文字へ制限しない。旧通知APIもタイトル・本文を切り詰めず渡す。

撤廃済みの上限で拒否するテストは削除する。正常系・形式・所有者・権限・競合・復旧の検証は維持し、大きな本文・応答・保存値が欠けずに往復する代表試験へまとめる。接続先や規格の必須条件を確認するテストは根拠を添えて残す。

## 時間制限と生成結果の保持

今後の設計・実装では、具体的な必要性のない時間制限を追加しない。保持TTL、待機期限、操作期限、タイムアウトなど、名称や実装箇所だけを制限の根拠にしない。「通常は十分」「メモリーを空けたい」「実装が簡単」という理由だけで、成果物の削除や処理の打ち切りを決めない。

OS・外部プロトコル・セキュリティ・データ整合性などの根拠がある制限は、対象、値、根拠、到達時の動作、成果物への影響を設計・レビューへ記録する。追加・変更した場合は、利用者へ理由と影響を必ず報告する。利用者が明示的に指定する待ち時間と、本体が根拠なく設ける固定期限を区別する。既存の値も、それが存在するだけで妥当とみなさない。

生成済みの原データは経過時間で破棄しない。メモリー負担は永続保全・必要時読込で解消し、保全先・復旧記録を時間制限付きキャッシュへ置き換えない。通信待ちの打ち切りと、既に得られた結果の保存は別に扱う。原本を失う削除は明示操作に限定し、別原本への安全な引き渡しが確認できた重複コピーの回収と区別する。

画像生成の未保存結果15分解放と、それを置き換える初期実装の要件は[バックグラウンドジョブ基盤と生成結果の永続保全](background-jobs-design.md)を正本とする。この方針の文書化だけでは、既存実装の期限を除去したことにはならない。

## 現在の保存契約

利用者が登録する設定一覧に、人為的な固定件数上限を設けない。コマンド・入力割り当て・exe名・リボン・トレイ・AI/MCP接続・Webアカウント・画像グループ・手動ボイスなどを同じ方針で扱う。メモリー、保存容量、画面表示や処理時間の負担は実際の設定量に依存する。保存時に黙って切り捨てない。

settings.json、端末設定、関連する名簿の固定合計サイズ上限も廃止する。設定値の型、IDの一意性、パスや文字列の形式、未知キー、秘密の保護、権限、revision競合、原子的保存は引き続き検証する。循環参照の禁止、OS/APIの契約、操作バッチ・実行キューの契約は、保存一覧の件数とは別に扱う。Appletが宣言するSchemaの意味上の制約も保持する。

## 確定設定に付随する索引

- `settings-indexes.ts`は正規化済みexe名・Applet IDのSetと、入力文字列から保存行位置へのMapを所有する。`parseSettings`完了時に準備し、実行側は同じ配列に対応する索引を参照する。exe名の照合は平均O(1)、入力候補の抽出は対象行数に比例する。複数の同義入力を統合するときは行位置をソートして保存順を守る。
- `settings-lookups.ts`はSettingsごとのカスタム定義ID/commandIdのMapと、解析済みの名前付きスタックを保持する。設定を再読込・保存すると新しいスナップショット用に作り直す。許可・公開状態・実行可能性は実行直前に現在値から判定する。
- カスタム定義とconfig・解析済みスタックは確定時に変更不可にし、定義と種類の版に対応するSchema検証結果を共有する。表示一覧は同じ設定・種類・提供元世代と利用可否の依存状態なら再利用し、入力監視・トレイ・リボンで全件検証を繰り返さない。1件の利用可否はID索引から現在の提供元で判定する。動的な利用不可理由に変更トークンがない提供元は一覧を再利用しない。
- 索引はWeakMapに持ち、JSONへ保存しない。索引対象の配列はfreezeして内容変更を防ぐ。編集途中の可変配列はキャッシュせず、その時点の内容から判定する。編集側は複製した次の設定を保存する。
- InputHostは別プロセスなので.NETのHashSetを設定受信時に用意する。同じ設定世代の同内容のexe一覧を共有し、キーとマウスの条件判定で再利用する。設定世代が変われば共有プールを更新する。元配列とHashSetの関係にはConditionalWeakTableを使う。
- WebプロファイルのID索引は名簿の置換時に更新する。一覧編集・並べ替え・所属更新・描画の繰り返し検索は、処理単位でMap/Setを作り、同じ全件走査の繰り返しを避ける。

全件表示・全件保存・動的な条件評価には必要な走査が残る。すべての処理をO(1)にする契約ではない。登録順、重複コマンドの実行、first/all、無効行、未知の保存ID、最新の許可判定を変えず、頻繁な照合と二重ループから改善する。
