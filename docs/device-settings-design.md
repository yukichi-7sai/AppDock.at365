# 端末別設定とAppletごとの設定保存先

状態: AppDock 0.57.0で実装（2026-10-18）。保存モードを設定ツールバーへ置き、本体の「表示」「一般」の設定JSON対象を常に端末専用とする。同2ページも同じチェックボックスをチェック済み・操作不可で表示する。保存仕様は[設定同期と保存領域](settings-sync.md)、[設定基盤](settings-foundation.md)、[Windows起動設定](launch-settings.md)、実測結果は[検証記録](../VERIFICATION.md)を参照する。

## 目的と決定

同じAppDockの配置を複数PCへ同期して使う場合に、Appletの有効状態と一部の本体設定を端末ごとに保持する。Appletの設定内容は、Applet単位で共有と端末専用を選択できるようにする。

| 対象 | 保存先・適用方針 |
| --- | --- |
| Appletの有効・無効 | 常に端末別JSON |
| Appletの「このPCで設定を保持する」 | この選択自体も端末別JSON。既定OFF |
| Appletの設定内容・開始までの秒数・ページ表示方法 | 上記がONなら端末別JSON、OFFなら共有settings.json |
| 本体の「表示」「一般」の設定JSON対象 | 常に端末別JSON。具体的な対象は下表 |
| その他の本体設定 | 引き続き共有settings.json |
| 認証・操作許可・Storage・Secrets・履歴・キャッシュ・Window状態 | 現在のPC専用rootの保存仕様を維持 |

端末専用にしたAppletでは、そのAppletの設定一式を共有側から独立させる。共有値との差分を項目ごとに継ぎ足す方式にはしない。端末専用設定が選ばれている間も、他のAppletと本体の共有設定は通常どおり同期する。

本体の端末専用項目は次の9キーを明示的に定義する。ページ全体の設定JSONを同じ保存先へ揃え、フォーム／JSON／ファイルを開く操作を一致させる。

| ページ | 設定キー | 内容 |
| --- | --- | --- |
| 表示 | host.theme | テーマ |
| 表示 | host.accentColor | アクセントパレット（既定ミント） |
| 表示 | host.customAccentDark / host.customAccentLight | カスタムの濃い色 / 淡い色（#RRGGBB） |
| 表示 | host.showHints | ヒントの表示（既定ON） |
| 表示 | host.shellProviders | 領域ごとのShell選択 |
| 一般 | host.soundEnabled | 音の再生 |
| 一般 | host.closeToTray | 閉じるとトレイに収納 |
| 一般 | host.startMinimized | 起動時にトレイに収納 |
| 一般 | host.startAtLogon | スタートアップ登録 |
| 一般 | host.runAsAdministrator | 常に管理者として起動 |
| 一般 | host.hardwareAcceleration | ハードウェアアクセラレーション |

一般ページの現在の起動状態・設定ファイルの診断や、操作許可画面へのリンクは、移動する設定値には含めない。認証・許可の既存保存先も維持する。今後の項目追加はページ名だけから保存先を暗黙決定せず、この分類定義へ追加して判断を記録する。

実装は本体の設定保存・UI・移行・復旧と通常publishを対象とする。実利用設定・Windowsの登録は変更せず、試験は隔離profileとfixtureで行う。commit・push・Release・実利用先deployは別操作とする。

## 現状と変更箇所

2026-10-18のソースを確認した。

- `src/main/core/settings.ts`のSettingsStoreは、EXE隣のsettings.jsonを1ファイルの正本として読み書きし、revision、外部監視、原子的置換、正常世代のバックアップを持つ。
- `src/main/core/applet-management.ts`は`extensions[id].enabled`、動的ページでは提供元の一覧内の`enabled`を保存する。`extensions.ts`等は同じ保存済み設定から起動・停止を判断する。
- Applet設定ページは`settings-catalog.ts`で`settings`、`startupDelaySeconds`、`pages[*].display`を編集対象として投影する。更新元は別の管理項目である。
- 本体の`host.startAtLogon`と`host.runAsAdministrator`は共有設定にある。WindowsLaunchは明示保存時のタスク操作とJSON保存を連携させ、失敗時には以前のタスクXMLを復元する。
- `data-paths.ts`のPC専用rootは`%LOCALAPPDATA%/at365/AppDock/profiles/<配置ID>/`。既存のwindow-state.json等は今回のJSONへ移さない。

WallpaperSlideshowのモニター一覧・画像フォルダー・表示方法・更新間隔等は、現在`extensions["at365.wallpaper-slideshow"].settings`にまとまっている。このAppletを端末専用へ切り替えると、その一式を各PCで独立して変更できる。

## ファイル配置と端末の識別

```text
AppDock.at365.exe
settings.json                 共有設定
settings-PC-A.json            PC-A用の設定
settings-PC-B.json            PC-B用の設定
data/                         既存の共有名簿・登録素材

%LOCALAPPDATA%/at365/AppDock/profiles/<配置ID>/
  settings-backups/            従来の共有設定の正常世代
    device/<端末キー>/         この端末のJSONの正常世代とinitialized.json
  settings-transactions/      保存途中の回復用。同期しない
  window-state.json           従来どおり
  ...                         認証・許可等の既存データ
```

`settings-<端末名>.json`もEXEの隣へ置く。ファイル自体はフォルダー同期・バックアップの対象にできるが、AppDockは起動中の端末に対応する1ファイルだけを適用する。「端末専用」は適用先の区分であり、ファイルを他PCへ転送しないという意味にはしない。

- 端末名はOSから`os.hostname()`で取得し、起動中は固定する。環境変数や任意のAPI引数から対象端末を指定しない。
- ファイル名は取得した端末名を用いる。Windowsの大文字・小文字を区別しない同一名を同じ端末キーとして扱う。JSON内のmachineNameもその規則で照合する。
- 空文字、区切り文字、制御文字、Windows禁止文字、末尾の空白・点など、不正なファイル名になる端末名は拒否する。別の文字へ置換して異なる端末を同じ名前へ丸めない。解決後の親ディレクトリーがEXEの配置先であることも検査する。
- 他の端末用JSONを列挙して選んだり、更新日時が新しいファイルを代用したりしない。参照・監視・保存・復旧は自端末用だけを対象とする。
- 同じ同期先を使うPCは端末名を一意にする。同じ名前のPC同士は同じ設定ファイルを参照するため、独立運用には別名が必要となる。追加のハードウェアIDや端末名簿は導入しない。
- 端末名を変更した場合は新しい端末として扱い、旧名ファイルを自動削除・上書きしない。引き継ぐ場合はAppDockを終了し、旧名の内容を新名ファイルへコピーしてmachineNameも変更する。旧端末用ファイルの自動整理機能は追加しない。
- EXE配置先を変えた場合は、共有・端末別JSONは持ち運べる一方、PC専用rootは既存仕様どおり変わる。Cookie、キー、操作許可、タスク登録まで移行されたとは表示しない。

## 端末別JSONの形式

共有settings.jsonのschemaVersionは当初1を維持し、端末別JSONには独立したschemaVersion:1を設ける。以下は端末用ファイルの例である。

```json
{
  "schemaVersion": 1,
  "machineName": "PC-A",
  "host": {
    "theme": "light",
    "accentColor": "mint",
    "customAccentDark": "#217a65",
    "customAccentLight": "#e1f3ec",
    "showHints": true,
    "shellProviders": {},
    "soundEnabled": true,
    "closeToTray": true,
    "startMinimized": false,
    "startAtLogon": true,
    "runAsAdministrator": false,
    "hardwareAcceleration": false
  },
  "extensions": {
    "at365.wallpaper-slideshow": {
      "enabled": true,
      "useLocalSettings": true,
      "configuration": {
        "settings": {
          "intervalSeconds": 120,
          "monitors": []
        },
        "startupDelaySeconds": 30,
        "pages": {}
      }
    },
    "example.notes": {
      "enabled": false,
      "useLocalSettings": false
    }
  },
  "collectionEnabled": {}
}
```

- hostは上表の12キーを扱い、省略キーは本体の現在の既定値を補う。themeとaccentColorは各定義の列挙値、customAccentDark/customAccentLightは#RRGGBB形式、shellProvidersは既存のShell指定規則、残りはbooleanとして検証する。省略されたhost・extensions・collectionEnabledは空objectとして補い、明示された不正な型は拒否する。Applet ID・ページID・秒数・表示方法等も既存の検証規則を再利用する。
- extensionsの各項目はenabledとuseLocalSettingsを必須とする。useLocalSettingsがtrueならconfigurationも必須。falseでも過去のconfigurationを保持できる。
- configuration.settingsは必須object。未宣言・未導入時の既存設定キーも保持する。startupDelaySecondsとpagesは任意で、欠落時はmanifest等の既定値を使う。共有側の値へは戻らない。
- configurationに含めるのはApplet設定ページで編集する上記3種類だけ。updateSource、リボン配置、通知種類設定、ショートカット、トレイ、共通名簿、認証、操作許可等を取り込まない。
- collectionEnabledは`{ "<owner>": { "<collectionKey>": { "<itemId>": true } } }`。動的ページの有効状態を構造化した識別子で保持し、区切り文字を連結した独自IDから復元しない。
- 未知のトップレベルキー、未知schemaVersion、machineName不一致、不正な型は拒否する。任意のhost設定や認証を端末用JSONへ書ける汎用上書き口にはしない。
- 読み取り上限は共有と同じく各4MiB、UI入力は既存の1MiB制限を維持する。IDの安全性・件数・深さの検証と、prototypeを変更するキーの拒否を共通化する。

## 読み取りと書き込みの契約

### 適用する設定の生成

mainで共有データ・自端末データ・現在適用する値を区別する。画面、runtime、設定コマンドには同じ合成済みの値を渡す。

1. 共有settings.jsonを既存の検証・復旧規則で読む。
2. 自端末のJSONを独立して検証・復旧する。
3. 表示・一般のhost9項目とAppletのenabledを端末側の値で置き換える。組み込みDefault Shellの常時有効という例外は維持する。
4. useLocalSettingsがtrueのAppletは、settings、startupDelaySeconds、pagesをconfigurationから一式で置き換える。配列・objectを共有設定と再帰mergeしない。
5. 動的ページの有効状態をcollectionEnabledから投影する。
6. 全体構造と、利用するAppletの宣言に従う検証を行い、従来のSettingsの形で各機能へ渡す。

Applet IDは共有設定・端末設定・導入済みmanifestの和集合として扱う。端末専用の設定が残るIDを、共有側の項目が消えたという理由で削除しない。共有項目がないOFFのAppletは設定objectを空とし、manifest等の既定値を使う。未導入IDの保持は自動起動を意味しない。

端末側に設定キーがなければ、manifestの既定値等の既存ルールを適用する。共有側に新しい値が届いても端末専用設定へ混ぜない。ローカルのキー削除は共有値の復活ではなく、当該キーの既定値へ戻す操作になる。

### 保存先の決定

すべての編集をmainの共通Coordinatorへ集約し、変更対象と現在の保存モードから保存先を決定する。呼出元がファイルパスや別端末名を渡す構造にはしない。

- 有効状態・保存モード・表示／一般のhost9項目は自端末JSONだけを変更する。
- Appletの設定一式は、現在のモードに対応するファイルだけを変更する。
- その他の本体項目・Applet更新元等は共有settings.jsonだけを変更する。
- 保存後に合成値を作り直し、従来のchanged経路から反映する。同値操作では保存しない。
- 共有ファイルへの保存は共有の元データに変更分を適用する。合成済みSettingsを丸ごとserializeして、端末の値を共有へ漏らさない。
- 保存失敗時に別の保存先へ代替保存しない。失敗値は従来どおり現在の画面内に保持する。

### 共有ファイル内の旧フィールド

共有ファイル内の表示・一般のhost9項目と`extensions[*].enabled`は初回移行の入力として保持する。起動時に共有ファイルから一括削除しない。移行後の端末では適用も更新もしない。

共有ファイルに新しいApplet項目を作る際、既存構造上必要なenabledはfalseを保存し、このPCでの有効化は端末側に保存する。旧フィールドを端末の最新状態へ追従させない。共有ファイル受信によってenabledが変わっても、このPCの起動・停止は変わらない。

旧版AppDockは端末別JSONを利用しないため、旧版と新版を同じ同期先で混在させると端末固有という契約を共有できない。実装時の更新案内へ記載し、同期して利用する本体は対応版へ揃える。旧版へ戻すための自動書き戻しは行わない。

## Appletの切り替え

| 操作・状態 | 結果 |
| --- | --- |
| 初めて「このPCで設定を保持する」をON | 現在の保存済み設定一式をconfigurationへコピーし、モードと同じ1ファイルの保存で確定 |
| 端末用configurationが残っている状態でON | 残っている端末用設定を再開。共有値で上書きしない |
| ON中の編集 | 端末用configurationへ即時保存 |
| OFFへ変更 | 確認ダイアログで共有へ反映／PC用を削除／PC用を保持を選択。保持を既定とする。成功後に共有設定を適用 |
| OFF中の編集 | 共有設定へ即時保存。残してある端末用configurationは変更しない |
| Appletを無効化 | 設定・保存モード・configurationを保持。保存先を変えない |
| Appletが未導入・削除済み | 設定を保持。再導入時は同じIDの状態を使用 |

切り替え前に送信済みの入力キューを待ち、現在の保存済み値とrevisionを確かめる。無効な入力や失敗値を暗黙にコピーしない。画面にそのような値が残っていれば切り替えを受け付けず、既存の入力エラーから修正または再読み込みできるようにする。全体の未保存状態や保存／破棄ボタンは追加しない。

OFFにする際は共有側も直前に再検証する。共有設定が読めない・対象設定が不正な場合はOFFを保存せず、現在の端末設定を維持する。ON再開時のconfigurationが現在の宣言で利用できない場合も切り替えを成立扱いしない。

共有への反映は対象Appletのconfiguration一式だけを置き換え、PC用configurationの削除・モード変更と同じトランザクションで保存する。有効状態・更新元・子ページのPC専用有効状態を共有へコピーしない。詳細は[既定値省略とリセット](settings-defaults-reset-design.md)を参照する。同文書の省略形式も読み取れるため、hostの省略キーは現在の既定値を補う。schemaVersionとmachineNameの識別検証は維持する。

保存モードの変更は有効化ではない。停止・無効のAppletを起動しない。有効なAppletの設定変更通知、開始待ちの再調整、ページ表示先の変更は、合成値に対する既存の適用経路を1回だけ実行する。起動・適用に失敗した場合は、保存結果と適用結果を分けて既存のエラー報告へ接続する。

### 動的ページとWebApplet

保存モードの単位は、manifestを持つ実AppletのIDとする。WebApplet等が生成する子ページには独立した保存モードを設けず、提供元Appletのモードに従う。親のsettings内にある一覧一式も選択した保存先へ格納する。

ただし、子ページの有効・無効は常にこのPC専用とする。共有・端末用一覧内の旧enabledは初回移行用の値として保持し、適用時はcollectionEnabledを優先する。子ページだけのON/OFFで一覧全体を端末用へコピーしない。

一覧編集では名前・URL・アカウント選択・順序等と、有効状態を分離して保存する。共有一覧を編集するときに、合成されたローカルenabledを共有側へ書き戻さない。新規行の共有enabledはfalse、このPCで明示的に追加した行の有効状態は端末側へ保存する。別PCへ到着した未知の子ページは既定で有効とする。端末側へ保存済みのOFFは保持する。

共有と端末用の一覧で異なる子ページIDが存在し得る。切り替えで見えなくなったページの有効状態・リボン配置・ショートカットを自動削除しない。戻したときに同じIDで復元する。名簿の到着待ち、UUID、既定ショートカットの一度だけの導入、参照中sessionの削除ガードは維持する。モード切り替えを新規導入と扱わない。

## 本体の表示・一般設定

表示と一般の設定JSON対象はすべて常時端末専用とし、共有へ戻すトグルは設けない。テーマ・音・GPU描画を含めて各PCで独立させる。Shell選択も、端末ごとにAppletの有効状態や使用可能なShellが異なることに合わせる。リボンの配置、通知の種類別設定、タスクトレイの割り当て等は引き続き共有とする。

theme、accentColor、customAccentDark、customAccentLight、showHints、soundEnabledは端末値の保存・受信から現在の共通適用経路へ即時反映する。soundEnabledをOFFにしたときの再生・待機中音声の取消と、TTS生成の扱いは[共通音声再生](audio-playback.md)に従う。hardwareAccelerationは早期起動から端末値を読み、変更後の再起動通知と完全終了後の反映を維持する。保存先の変更を、起動専用項目の即時反映へ置き換えない。

### 本体の起動設定

host.startAtLogonとhost.runAsAdministratorは保存モードの選択対象にせず、一般設定に「このPC専用」と表示する。設定値は起動初期、管理者起動の判断より前から同じ合成処理で取得する。別に共有値だけを読む早期起動経路を残さない。

- 設定変更はWindowsLaunch.saveとCoordinatorを連携させる。事前検査、OS操作、保存直前のrevision照合、端末JSONへの保存、失敗時のタスクXML復元を維持する。
- タスクのSID、配置ID、元EXE、引数、所有権、RunLevel、同一ユーザーの検査は維持する。
- 共有JSON・端末JSONの受信だけでは、タスクの作成・更新・解除や即時の昇格・降格を行わない。現行どおり、OS登録は明示保存で変更する。
- 管理者起動の設定が自端末JSONの受信で変わった場合、次回の通常起動でその保存済み値を使う。起動時のUACと取消後の通常起動、再起動経路は現行契約に従う。
- JSONへの保存成功、Windowsの実登録、現在のトークンを別々に表示・検証する。OFFの保存で現在の管理者プロセスが降格したとは扱わない。

その他の本体ページを今回まとめて端末用へ移さない。追加の端末専用化は後続の要件で判断する。

## 初回移行と新規項目

### 既存配置の初回移行

自端末JSON、同名用の正常バックアップ、初期化済み記録のいずれもない場合に限り、検証済みの共有設定から初期ファイルを作成する。

1. 共有設定の有効な保存済み値を読み、表示・一般のhost9項目と全Appletのenabledを引き継ぐ。manifestを実行なしで読み、動的ページは宣言に基づいて現在の一覧を検証して子のenabledも引き継ぐ。runtime起動やアカウント操作を初期化の前提にしない。
2. 全AppletのuseLocalSettingsをfalseにする。configurationはまだ作らず、従来の設定内容をそのまま使う。
3. 共有と自端末用パスを再確認し、作成先が存在しない場合だけ端末JSONを原子的に作成する。他の処理が先に作成していたら、そのファイルを検証して採用する。
4. 端末JSONの保存後、PC専用の`settings-backups/device/<端末キー>/initialized.json`へschemaVersion:1とmachineNameを原子的に保存する。この記録まで完了してから、通常の起動判断・設定編集へ進む。移行のためのWindowsタスク操作、共有settings.jsonの書き戻し、Appletコマンド実行は行わない。

初回ファイルの保存に失敗した場合は、共有保存へ戻して処理を続けない。設定初期化のエラーとして起動・編集を制限し、再試行の案内と保存先の確認を提供する。破損ファイルが存在する場合も「未作成」とは扱わない。

initialized.jsonは、バックアップ保存に失敗した後で端末JSONが欠落しても初回移行を繰り返さないための最小記録であり、設定値や他端末一覧は持たない。正常な端末JSONを初めて読み込む際も記録を作る。端末JSONの作成後・記録前に終了した場合は、その正常な端末JSONを採用して記録だけを補完する。記録があるのに端末JSONも正常世代もない場合は復旧待ちとし、共有から再生成しない。

未導入Appletのレコードは引き継げるが、その動的ページの構造をキー名や値の形だけで推測しない。初回時点で宣言を取得できなかった子のenabledは後から暗黙移行せず、認識時の既定falseとし、必要ならこのPCで有効化する。未導入の設定値自体は保持する。

### 初期化後に初めて見えるApplet

初期化済み端末へ共有設定や新しいAppletが届いた場合、端末側の未登録IDはenabled:true、useLocalSettings:falseとして扱う。共有側の旧enabledをもう一度取り込まない。導入操作がこのPCでの有効化を含む場合は、その操作の端末用保存として明示的に実行する。Default Shellの常時有効は例外とする。

端末ファイルが欠落した場合も、正常バックアップがあればそれを使って復旧状態へ移る。共有からの初回移行を繰り返して、このPCの選択を置き換えない。端末名変更・別配置への新規導入は前述のとおり新規初期化となる。

## 共通保存基盤・競合・復旧

### mainの責務

内部構成は次の責務へ分ける。クラス名は実装時に調整できるが、保存先の判定を各機能へ分散させない。

| 要素 | 責務 |
| --- | --- |
| SharedSettingsStore | 共有の元データ、検証、ファイル監視、従来の正常世代 |
| DeviceSettingsStore | 自端末JSONの元データ、検証、ファイル監視、端末用の正常世代 |
| SettingsCoordinator | 合成値、保存先の分類、共通revision、保存の直列化、切り替え、復旧調停 |
| 各UI・runtime・機能サービス | 合成済みのSettingsの利用。変更はCoordinatorへ依頼 |

SettingsStoreの既存利用箇所はCoordinatorを正本とするfacadeへ接続する。SettingsInputSession、設定ページ投影、SettingsCommands、AppletManagement、Host APIの自己設定、Node/.NET起動時設定とsettingsChanged、更新・移行・既定値登録等を対象にする。`settings.save(effective)`やupdateExtension等の直書き経路もすべて洗い出し、共有の元データへ端末値をserializeする経路を残さない。

### revisionとファイル監視

- 自端末と共有の両ファイルに、現在のwatch＋poll、安定bytesの確認、検証後の採用を使う。他端末用JSONは監視しない。
- UI/APIのrevisionは両Storeと保存モードを表す1つの不透明なrevisionとする。既存の起動ごとの識別子も維持する。
- 共有側の変更が端末用設定に隠れて合成値を変えない場合でも、共有の元データが変わればrevisionを進める。OFF切り替えや共有保存が古い値を前提に実行されないようにする。runtimeへの設定通知は適用値が変わったときだけ行う。
- 保存前に両ファイルを再照合し、UIはbeforeと現在値に加えて保存モードの一致も確認する。編集中に別の操作でモードが変わったら、別の保存先へ入力を転送せず競合として拒否する。
- 共有の受信は従来どおり届いた正常ファイルを採用する。PC間の三方向マージや設定履歴からの自動統合は追加しない。端末ファイルも正常な受信値を採用するが、共有の受信から端末ファイルを再生成しない。

### 複数ファイルを変更する操作

通常のトグルや設定入力は保存先が1つとなり、既存の原子的置換を使う。一般ページの部分JSONやWebApplet行編集等、共有と端末の両方が変わる既存の一括操作も維持する。

2ファイルを同時にrenameできるとは扱わず、Coordinatorで回復可能なトランザクションにする。

1. 全入力を検証し、対象ファイルのbefore bytes/hash、変更後のbytes/hash、必要な関連素材・OS操作を確定する。無変更ファイルは対象に入れない。
2. PC専用rootのsettings-transactionsへ操作ID・対象の固定パス・before/after・進行段階を保存する。ジャーナル自体も原子的に更新する。任意パスを復旧対象として信頼せず、自配置の2設定ファイルと宣言済み関連処理だけを許す。
3. OS/素材の既存トランザクションと連携し、各置換直前に期待bytesを照合して順次保存する。保存処理中は同一プロセス内の編集・監視による再入・再起動を調停する。
4. 全保存後にジャーナルのcommittedを永続化してから、新しい合成値とrevisionを1回だけ通知して完了を返す。ファイル監視は終了後に再照合する。次回起動時にcommittedを確認した操作はロールバックせず、保存結果を読み直してジャーナルを回収する。
5. 失敗時は、この操作が書いたafter bytesと今のファイルが一致するものだけbeforeへ戻す。外部更新されたファイルをロールバックで上書きしない。OS登録も、この操作による変更と確認できる範囲で既存のXML復元を行う。
6. ロールバック不能・途中終了ではジャーナルを残し、次回の通常適用前に同じ照合で復旧する。未解決の間は対象保存と通常の設定適用を保留し、共通エラー通知と復旧導線を示す。

起動時の復旧でUACやAppletコマンドを自動実行しない。タスク復旧に昇格が必要なら明示操作へ誘導する。ジャーナルには設定内容が含まれるため共有フォルダー・ログ・MCP応答へ出さず、成功して役目を終えたものは削除する。同期先の別PCには中間状態が順番に届き得るため、異なるPCをまたぐ原子性まで保証しない。

### 読み取り障害とバックアップ

共有と自端末の正常世代を分け、各last-goodと直近20世代をPC専用rootへ保持する。従来の共有backupの場所と読取互換性は維持する。端末バックアップは端末キーとmachineNameを照合し、他端末の世代から回復しない。

片方のファイルの破損・欠落・ロックでは、そのStoreの直近正常値を維持して障害を表示する。端末用設定を共有値で代替しない。起動時に端末用の正常値を確保できなければ、通常のApplet起動と自動管理者起動を進めず、既存の起動前の復旧ダイアログで正常JSONの選択・保存先確認・再読み込みを提供する。

共有側が一時的に読めない場合、正常な端末用設定の単独編集は許可できる。ただし保存はその端末ファイルの正常性と対象の保存モードを照合し、共有を変更する操作・共有へ戻る操作・共有値をコピーする初回ONは拒否する。全ファイルを常に必須とするrevision検査と、この障害時の限定保存を区別する。

設定状態には共有／このPCのどちらに問題があるか、復旧対象、使用中の正常世代を示す。復元は選択対象だけに行い、他方の正常ファイルを巻き戻さない。本文・履歴・読み上げには設定の生値やローカル診断のフルパスを含めず、詳細ログ・保存先を開く導線を使う。

## UIと外部API

### 設定ツールバー

Applet一覧の有効トグルに「このPCの有効状態」と分かる説明を付ける。保存モードは、フォーム／JSONとファイルを開くボタンがある既存のSettingsPageLayoutのツールバーへ置く。本文内には同じトグルを重複配置しない。全体設定とApplet詳細で同じモデル・部品を使う。

```text
Applet
[フォーム] [JSON]   [✓ このPCで設定を保持する]   [ファイルを開く]
                   設定JSON: このPC専用 · 変更は自動で保存されます。

本体の表示・一般
[フォーム] [JSON]   [✓ このPCで設定を保持する（操作不可）] [ファイルを開く]

本体の共有設定ページ
[フォーム] [JSON]   設定JSON: 共有                 [ファイルを開く]
```

Appletでは既定OFFのチェック式トグルを使い、ONで端末専用、OFFで共有とする。本体の表示・一般にも同じチェックボックスを置き、チェック済み・操作不可とする。「設定JSON」の保存先表示はフォームとJSONのどちらでも見えるようにする。APIキーや認証等、設定JSONとは別管理の項目は既存の「このPCへ暗号化保存」等の説明を維持する。

ON/OFFの説明には、初回コピー、端末用設定の再開、OFFでは共有へ戻ることを短く示す。切り替えは即時保存とし、通常操作に別の確認ダイアログを追加しない。停止・無効時も操作でき、設定画面を開くだけで起動しない。子ページは保存モードの提供元Appletを案内し、同じ選択肢を重複表示しない。

ツールバーが狭い場合は保存先と保存状態を次の行へ折り返す。主要なラベルをアイコンやhoverだけへ置き換えず、ファイル名は補助表示へ回す。切り替え・JSONへの移動で自動スクロールや不用意なフォーカス移動を加えない。

### JSON表示とファイルを開く操作の連動

フォーム／JSONは編集方法の切り替えであり、保存先の選択とは独立する。JSONは現在適用しているページの許可範囲だけを表示し、保存先ファイル全体やmachineName/useLocalSettings等の制御項目を表示・編集する口にしない。端末用ファイルのconfigurationという内部包みも、従来のページJSONへ持ち込まない。

保存モードを変えたら、フォームの値、部分JSON、保存先表示、ファイルを開く対象を同じモデル更新で切り替える。JSON表示中にもツールバーのトグルを操作できるが、不正入力・保存失敗・送信待ちを先に処理する契約はフォームと共通とする。別のモードで作成した古いJSONを新しい保存先へ自動転送しない。

| 表示対象 | 設定JSONの主な保存先 | ファイルを開くボタン |
| --- | --- | --- |
| Applet・保存モードOFF | 共有settings.json | settings.jsonを開く |
| Applet・保存モードON | 自端末`settings-<端末名>.json` | 自端末ファイルを開く |
| 本体の表示・一般 | 自端末`settings-<端末名>.json` | 自端末ファイルを開く |
| 本体のその他のJSON対応ページ | 共有settings.json | settings.jsonを開く |

現在のページID・revision・保存モードを含む同じモデルからJSON範囲と実ファイルの対象を生成する。mainでもクリック時に再検証し、古い画面から別の保存先を開かない。操作引数はパスではなく許可された対象区分とする。開く操作で不足ファイルを自動生成せず、未作成・読み取り不能ならその状態を表示する。

動的ページの一覧JSONなど、設定本体と常時端末専用の有効状態が同じ編集に含まれる場合は、モデルが編集可能パスごとの保存先を解決する。対象が実際に2ファイルになる場合だけ「設定JSON: 共有＋このPC」と表示し、ファイルを開くボタンを対象選択メニューにする。通常の単一保存先ページへ常時2択を持ち込まない。表示／一般は上記9キーを一括で端末用にするため、この混在にはならない。

一般の設定ファイル診断欄には、ページの保存先に関係なく共有と自端末の両方の保存先・状態・対象別復元を示す。ツールバーは現在ページのファイルを開く入口、診断欄は設定基盤全体を確認する入口とする。他端末の一覧・編集機能は作らない。

### 外部API

既存のApplet設定API・生成設定コマンド・MCPは、そのPCで現在適用する値を読み、選ばれている保存先へ書く。automation公開項目、非公開キー、自己設定capability、expectedRevision、dryRun、再入防止、コマンドと設定の独立許可は維持する。別端末の値・保存ファイル・認証は返さない。

保存モードの切り替えは初回はローカルUI専用とする。Appletの自己設定やMCPから共有／端末専用を変えるAPIは追加しない。有効化・無効化コマンドのIDと必要権限は維持し、保存先だけをこのPC用へ変更する。restartは引き続き有効化しない。

設定画面の本体統合は[別設計](settings-host-ui-design.md)であり、この保存設計の前提条件にしない。実装時点の設定Surfaceへ接続し、後から統合してもCoordinatorと保存契約を変えずに済む構成にする。

## 実装の順序と影響先

1. 端末名の解決、端末JSONスキーマ、独立バックアップ・監視・初回移行を追加する。純粋な設定合成と保存先分類を分離して試験する。
2. Coordinatorと共通revision、原子的保存・複数ファイル復旧を実装し、すべての設定保存口と早期起動を接続する。
3. Applet有効状態、動的ページ、開始待ち、設定通知、WindowsLaunchを新しい合成値へ接続する。設定モードのUIと部分JSON・復旧表示を追加する。
4. 影響する契約・GUI・固定EXEを検証し、実装差分と保存境界をレビューする。現行仕様文書と更新案内を整合させ、問題を解消してから版更新・通常publishを行う。

本体の保存形式、設定項目、保存ファイルが増えるため、実装時は[共通手順](development-workflow.md#版更新の判断)に従ってAppDockをマイナー更新する。具体的な版は着手時の版から決める。既存Appletへ同じ設定オブジェクトを渡す契約を保ち、変更しないAppletの版更新・再発行を行わない。共通APIの変更が必要と判明した場合だけ、対応型・文書・Node/.NET試験・最低ホスト版の影響を確認する。

実装版は0.57.0。`device-settings.ts`が形式・合成・保存先分類、`device-settings-store.ts`が既存Storeのfacadeと回復処理を担う。保存先切り替えの応答は範囲とrevisionだけを返し、設定全体を設定ページモデルへ返さない。0.58.0では[本体統合](settings-host-ui-design.md)を実装し、本体の共通画面でも保存先・JSON・ファイル操作の連動を維持する。

実装時の文書更新対象はsettings-sync、settings-foundation、launch-settings、automation、applet-development/extensions、usage.mdの保存先、必要な更新・配布手順。publish/deploy/updateが`settings-<端末名>.json`を生成物と誤認して同梱・上書き・削除しないことも確認する。commit・push・Release・実利用先deployは実装・通常publishと分離する。
