# カスタムコマンド拡張の段階的実装計画

状態: A〜Dの実装・検証・ローカル発行を完了。AppDock 0.62.1／WindowsTools 0.2.0。更新日: 2026-10-18。[拡張設計](custom-command-types-design.md)を正本とする。既存のMCPハブ第1〜4段階の後続であり、その実装をやり直す計画ではない。

## 実装順序

| 段階 | 実装範囲 | 完了時に確認できること |
| --- | --- | --- |
| A. 共通説明文 | 単一のversion 2、全定義のdescription、CRUD・JSON・UI・公開カタログ | MCP種類とApplet種類の説明を保存・再取得でき、同じMCP接続のコマンド一覧へ反映される |
| B. 本体のキー送信 | 本体種類、既存入力APIへの接続、MCP側sendInput許可 | WindowsToolsなしで単独キー／組合せを実行でき、公開済み定義をMCPから使える |
| C. コマンド／プロセス起動 | 共通起動サービス、直接／cmd／PowerShell入力、独立許可 | ローカル入力・Applet共通API・MCPの保存型コマンドから起動受付を確認できる |
| D. WindowsToolsの撤去 | 旧キー送信の設定・動的コマンド・コード・試験の除去 | 旧機能が表示／登録されず、12固定コマンドと既存ユーティリティが維持される |

順序はA→B→C→Dを基本とし、Dは少なくともA・Bの必要検証が成功してから行う。説明文はB・Cに先立ち既存の全種類へ適用する。MCP実行種類はAの確認対象として扱う。

**WindowsToolsと旧カスタムコマンドの設定移行・互換維持は実装しない。** 既存設定を作り直してよい前提で、現行形式をversion 2に一本化する。旧定義の変換・インポート・旧IDの対応表・自動付替え・旧設定の清掃を、この計画へ追加しない。

## A. 共通説明文と保存版

1. 現行の保存形式をversion 2へ揃える。version 1専用readerや変換を追加せず、一般的な未対応版保持を維持する。
2. 共通definition、add／update／JSON差分の項目一覧、説明だけの変更時の実行継続を対応する。
3. 共通ダイアログに複数行の説明を追加し、種類変更・取消・競合・再起動での扱いを揃える。
4. publicCommandsと一般commands.listへ説明を返す。管理許可なしでも公開済みの説明を読めることを確認する。
5. カスタムコマンドページのJSON編集から、新形式の一覧を明示保存して作り直せるようにする。旧IDは引き継がず、必要な割当を選び直す手順と、複数PCの本体更新順を文書化する。

保存版の更新と各種類のconfigVersion、typeRevision、既存の安定commandIdを混同しない。1,000文字の説明が多数ある場合の設定・API本文サイズも確認する。

## B. キー送信種類

1. 本体／Appletから呼べる共通の入力実行ヘルパーへ、ホスト発行の実行元と許可の検査を揃える。
2. `appdock.input.sendKeys`のSchema、送信用文法の検証、入力部品、providerを追加する。
3. MCP側sendInput許可を初期OFFで追加し、既存Applet許可・通常の入力・MCP→Applet経由を確認する。
4. 専用ネイティブ入力先へ送信し、最前面・開始対象・修飾キー待機・取消・連続操作・押下／解放を確認する。

既存WindowsToolsのキー送信は、この段階ではまだ撤去しない。新しい種類で同じ操作が成立することを比較できる状態にする。

## C. プロセス起動種類

1. 共通の型・検証・許可・起動サービスを追加し、Applet向け`processes.start`へ接続する。
2. 本体種類と3モードのフォームを追加する。直接引数は配列で保持し、cmd用の組立てを通常のargvから分ける。
3. runProcessesのApplet／MCP許可を初期OFFで追加する。MCPは保存型コマンドからだけ起動する。
4. 専用のargv記録fixture、短命CLI、使い捨てGUIを起動する。起動成功と、CLI完了／アプリの効果を区別する。
5. 隔離したAppDockの終了・再起動後も起動したGUIが継続し、標準入出力がRPCを破壊しないことを確認する。試験が作ったプロセスは試験で回収する。

各モードの引用符とコンソール指定・親終了後の寿命を実Windowsで確かめる。実装は専用ネイティブworkerのProcess.Startへ集約した。失敗時に別モードへ切り替えるfallbackを入れない。

## D. WindowsToolsの旧機能撤去

1. manifest、Shortcut、SendAsync、send.<id>生成、件数UI、キー送信専用の試験／説明を除去する。
2. 12固定コマンドのIDと登録、消灯／取消、自動ロック、ウィンドウ操作の設定／実行を維持する。
3. 本体の入力試験を本体の新種類へ接続し、WindowsToolsを入れない隔離profileでも検証できるようにする。
4. 旧IDが新IDへ変換されず、残った割当が既存の利用不可表示になることを確認する。旧データを製品の起動処理で触らない。
5. 利用者向けに、新規登録と割当を選び直す手順を記載する。通常の本体入力API・SDKは削除しない。

## 必要な検証

| ID | 確認項目 | 受入条件 |
| --- | --- | --- |
| E01 | 単一形式／保存 | 新規・CRUD・JSONがversion 2へ保存。未対応版からはJSONで新しい一覧を明示保存でき、旧定義の自動取込みや旧IDの付替えを行わない。dryRun／競合失敗ではファイル不変 |
| E02 | 未対応版 | version 1／未来版を読込だけで変換・破棄せず実行停止し、別ページ保存でも保持。旧形式専用の実行・編集・移行経路を追加しない |
| E03 | 全種類の説明 | 本体3種類とNode/.NET/native種類で作成・変更・消去・未入力・改行・上限・不正文字を同じ規則で処理 |
| E04 | 動的な公開 | 同じMCP接続で説明編集・追加・削除が一覧へ反映。外側tools/listの名前・Schema・注釈は不変。公開OFFは取得／直接実行不可 |
| E05 | 説明だけの編集 | ID・割当・configを維持し、実行中の処理と種類のtypeRevisionを変えない |
| E06 | UI／保存経路 | 即時反映と登録ダイアログのOK／取消、IME、入力保持、競合、明暗／狭幅、共通JSON・APIを確認 |
| K01 | 送信用の文法 | Enter／F5／修飾キー／Winを受理し、重複修飾キー・未知キーを拒否。既存SDKの文法と一致 |
| K02 | 実入力 | 専用ウィンドウ、デスクトップ起点のシステムキー、開始対象の変更、通常ホットキーとジェスチャー連続実行を確認 |
| K03 | 入力の取消／失敗 | 押下中の待機・取消・部分送信でキーを残さない。前面を奪ったり別Windowへ送信したりしない |
| P01 | 起動と引数 | 空白／日本語／引用符／空引数／末尾バックスラッシュ、cmdの特殊文字、PowerShell本文をfixtureで照合 |
| P02 | 副作用なしの管理 | 保存・dryRun・一覧・説明編集でプロセスを起動しない。ファイル未発見・権限不足・不正cwdは安全な失敗 |
| P03 | 起動の寿命 | processStartedを終了成功と扱わず、AppDock終了後もGUIが継続。起動前取消と結果不明を区別し、自動再送しない |
| G01 | 独立した許可 | 新規許可はOFF。管理許可だけでは実行不可。直接AppletとMCP→Appletの双方で元callerを保持し、一覧と実行の判定が一致 |
| M01 | 既存MCP種類 | 説明の追加後もtoolRevision、固定arguments、ジョブ状態／取消、接続先／ツール公開制約を維持 |
| W01 | WindowsTools撤去 | 旧設定UI／send.<id>がなく、12固定コマンドは維持。旧定義の変換・割当付替え・自動清掃を行わない |
| F01 | 最終配布物 | 対象の版・feed・hash・隔離起動、保存復元・固定EXEで各種類の実行を確認。fixture非同梱 |

製品のキー送信は専用入力先、プロセス起動は試験が作ったものだけを対象にする。MCPは隔離サーバーを使い、実SwitchBot操作などを回帰試験として繰り返さない。検証結果・実環境の未確認範囲はVERIFICATIONへ記録する。

## 作業段階と完了の扱い

各段階の実装は[共通手順](development-workflow.md)に従い、必要な検証・レビュー・対象モジュールの版更新・通常publish・成果物確認まで行う。途中修正や再発行だけで同じ変更の未公開版を重ねて増やさない。Dで変更するWindowsToolsも自身の版と発行物を更新する。

コミット依頼時は成功した検証を試験ごとに照合して再利用し、不足分だけ追加する。コミット・プッシュ・GitHub Release・実利用先deployはそれぞれの依頼に従う。利用中の設定は変更せず、検証には隔離profileを使用する。

2026-10-18の完了記録は、本体とWindowsToolsの`VERIFICATION.md`、各repoの`.artifacts/custom-command-types-20261018/validation.json`を参照する。固定EXEで本体3種類、動的説明文、許可、再起動と起動後GUIの継続を確認し、WindowsToolsの固定12コマンド・旧設定の非移行も確認した。
