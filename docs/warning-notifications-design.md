# 共通の警告通知

## 目的と適用範囲

処理の最終失敗は既存の[共通エラー通知](error-reporting.md)で扱う。処理失敗が確定していなくても利用者の確認・対処が必要な状態には、本体の共通「警告通知」を使う。

既存のNotificationService / TypedNotifications、通知履歴、Shell、Windows表示、読み上げ、共通ログへ接続する。別の通知配信経路や保存ファイル、MCP / Applet向けの任意警告発行APIは追加しない。

## 種類と利用者の設定

識別子は `host / warnings / attention-required`、レベルはwarning。通知設定のAppDock欄で「エラー通知」「警告通知」の順に表示する。既定はON、バナー、閉じるまで表示、読み上げOFF。表示先・時間・読み上げを既存の `notificationPreferences.overrides` で変更する。バナー・デスクトップ・Windows通知の組み合わせと通知センターのみを自由に選択できる。通知全体のOFFは設けない。エラー通知、設定の再起動要求から独立させる。

## 共通入口と状態の寿命

本体内部の `WarningReporter.episode()` を使う。発行元がeventId/source/title/code/messageと必要な操作を渡す。通知と履歴には短い原因・対処・警告コードを保存する。診断情報 `logDetails` は発行元が安全性を確認した固定説明とローカルパスだけを渡し、通知・履歴・読み上げには含めない。例外本文、JSON本文、Cookie、認証情報、ファイル内容、対象内のファイル名一覧は収集しない。

- 同じ状態の再評価・画面の往復・再描画は新規発行にしない。
- 原因や対象が変わった場合だけ共通ログのwarningレベルへ記録する。各対象を独立したログ行にし、全体の切り詰めで後半の対象を失わない。
- アクティブ通知の内容更新は同じID・期限を維持し、読み上げを再発行しない。
- 閉じる・期限切れ・配送失敗後は、同じ状態の間に復活させない。本体ログの状態は更新する。設定の変更で過去の警告を再送しない。
- 状態が解消したら発行元がresolveし、現在の通知だけを終了する。その後の再発は新episodeにする。
- 起動中のepisodeはメモリーだけに置く。次回起動時は現状を再評価し、残っていれば新規に通知する。通知履歴も起動中だけ保持し、既読管理は行わない。
- 通知・ログ自体の障害を再帰的に警告通知へ流さず、元の処理を失敗にしない。

## 検証

共通の種類・設定・episodeの更新/抑止/解消/再発・安全な履歴とログは`tests/warning-reporter.test.cjs`で確認する。通知設定の操作は既存の通知GUI試験、旧残存チェックの非実行と実ファイルの保持は`scripts/file-watch-assistance-ui-test.cjs`で確認する。専用の旧残存チェック機構とその試験は削除したが、MCP接続・カスタムコマンド・タッチパッド等の共通警告は維持する。
