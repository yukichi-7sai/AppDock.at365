# 画像ライブラリーのページ化と共通画像ギャラリー

状態: 工程A〜Eを実装し、Fの大量画像・遅延取得の確認まで実施（AppDock 0.74.6 / WallpaperSlideshow 0.7.2、2026-10-21）。管理ページ・画像選択・壁紙履歴に共通カード、拡大表示、独立したサイズ保存を適用した。512枚・64グループ・4096所属の隔離GUIと画面外の遅延応答を検証した。実測したFの範囲と未確認事項は各VERIFICATIONを正本とする。開始時の基準はAppDock 0.73.9 / main `ed6c780`、外観の参照元はWallpaperSlideshow 0.6.4 / main `00bc835`。

左にグループ、右に画像カードを置く画面を採用し、ページ内でカードサイズを変更できるようにする。WallpaperSlideshowの壁紙履歴を共通ギャラリーの外観の基準とする。画像の保存・参照・グループの現行契約は[共通画像ライブラリー](registered-images.md)、ページの責務は[Shellのページ表示](shell-pages.md)を正本とする。

## 1. 今回の設計範囲と到達点

最初に画面・操作・保存・共通部品・実装順序・受け入れ条件を設計し、続く工程で共通部品と本体の独立ページを一緒に実装した。現在の利用方法と追加ルールは[共通画像ライブラリー](registered-images.md)と[共通ギャラリーの利用](image-gallery.md)を参照する。

実装範囲は次のとおり。表示と保存の責務を分け、既存の選択・履歴操作を各adapterで維持する。

- 本体の独立した「画像ライブラリー」ページと、リボン・コマンドからの入口。
- 左のグループ一覧、ファイル名検索、登録画像の一覧、拡大プレビュー。
- ページ上の「画像サイズ」スライダー、画面幅に応じた列数変更、PC別・画面別のサイズ保存。
- 画像追加、単一画像の所属編集、複数選択によるグループへの追加・解除。
- グループの追加・名前変更・削除・並べ替え。
- 原画像を確認後にごみ箱へ移し、全グループの所属から外す。使用中の画像は先に使用先の設定を解除する。
- 共通ギャラリーを管理ページ、既存の画像選択ダイアログ、WallpaperSlideshowの壁紙履歴へ適用。
- 既存の原画像、画像参照、親ダイアログの確定・取消、履歴の操作契約の維持。

原画像の名前変更・未使用画像の自動整理、画像加工、階層グループ、タグとは別の分類方式、お気に入り、使用先の逆引き、ドラッグ＆ドロップ登録、URLからの取得は後続候補とする。NASへの保存先変更は[共有場所の設計](shared-settings-location-design.md)の別工程。本書を理由に既存ファイルをコピー・移動・削除・移行しない。

## 3. ページへの入口

| 入口 | 決定 |
| --- | --- |
| 標準リボン | `image-library`、表示名「画像ライブラリー」、画像アイコン。新規の既定順はホームの次、上寄せ |
| 保存済みリボン | 既存のorder・hidden・bottom・グループ・表示名を尊重。新項目は既存の未配置項目の規則で追加し、保存済み配列を自動書換えしない |
| コマンド | `appdock.image-library.open`、「画像ライブラリーを開く」。パレット等の共通コマンド経路を使用 |
| 設定 | 同名カテゴリ・案内ページ・検索アンカーを除去。既存の画像設定入力は維持 |
| 画像入力 | 今の画像選択ダイアログを開く。管理ページへ遷移させない |
| 再起動 | 既存の`--restore-view`によるページ復元へ新ルートを追加。通常起動の既定ページの規則は変更しない |

ページルートは`image-library`、Shell領域は`page.image-library`とする。本体管理機能として、通常Appletの有効化・起動に依存させない。リボンで非表示にしてもコマンドから開ける。

設定カテゴリの除去はデータ項目`imageLibrary.groups`の廃止ではない。設定の取得・同期・全体JSON編集は保存済みグループを維持する。原画像や後述のカードサイズを設定リセットで削除しない。

## 4. 画面構成

```text
画像ライブラリー                                      ＋ 画像を追加
AppDockで使う画像を、ひとつの場所に。
────────────────────────────────────────────────────────────
すべて          枚数 │ ファイル名で検索     画像サイズ  小 ─●─ 大
未分類          枚数 │ グループ名・該当枚数
                    │
グループ        …   │ ［画像カード］［画像カード］［画像カード］
  写真          枚数 │
  アイコン      枚数 │ ［画像カード］［画像カード］［画像カード］
  プロフィール  枚数 │
＋ グループを追加    │ さらに表示
```

### 4.1 レイアウト

- ページは本体の本文領域全体を使う。初期余白は24px、広い画面は32px、狭い画面は16pxを基準とし、本文の最大幅は壁紙履歴と同じ1480pxとする。
- 左のグループ列は200pxを基準、本文との間は24px。グループ一覧のスクロールは画像一覧から独立させる。
- 右のツールバーに検索とサイズ変更を置き、その下にグループ名・該当枚数と一覧を置く。本文を覆う固定フローティング操作は追加しない。
- ページ見出しと右のツールバーは一覧スクロールの外に置く。途中の画像を見ながらサイズを変えられるようにし、選択時の操作列も一覧を覆わずに領域を確保する。
- ギャラリーは本文内の単一スクロール領域とする。管理ページに旧一覧の430px上限や入れ子の縦スクロールを残さない。
- ページ本文幅760 CSS px未満ではグループ列を上部の「グループ」選択欄と管理メニューへ置換し、検索・スライダーは折り返す。左案のレスポンシブ表示であり、別レイアウトを保存する設定は作らない。
- 320 CSS px相当の幅、拡大表示でも横にはみ出さない。長いグループ名と枚数、操作メニューの領域を分ける。

### 4.2 グループと検索

- 「すべて」「未分類」は仮想一覧、その下に保存順のグループを並べる。選択は背景・枠・文字で示す。
- 枚数は重複を除いた画像参照の件数。複数所属があるため、グループ枚数の合計を全体件数として扱わない。
- 左の枚数は検索に左右されない全件数、右の枚数は現在のグループと検索条件に一致する件数とする。
- 現行同様、保存済み所属の未到着画像も一覧へ含める。「未分類」はどのグループにも所属しない画像。読取待ちと未分類を同じ意味にしない。
- 検索対象はファイル名、大文字小文字を区別しない。並び順は現行のファイル名順を維持し、新しい日時メタデータや並び順設定を追加しない。
- 検索は入力中に反映する。検索専用入力のIMEとEscapeの扱いを維持し、設定値のblur/Enter確定を検索へ強制しない。
- グループ切替時は検索文字列を保持する。フィルター変更時は複数選択を解除し、先頭から表示する。サイズ変更やデータ再取得では選択を解除しない。
- 最初の64件を表示し、「さらに表示（残りN件）」で64件ずつ増やす。件数は追加表示済み件数に限定しない。

### 4.3 画像カード

| 要素 | 決定 |
| --- | --- |
| 外観 | 壁紙履歴の14px角丸、細い枠、控えめな影、カード間20pxを基準 |
| 画像枠 | 16:10、縮まない領域。読み込み前も同じ高さを確保 |
| ライブラリー・選択画面 | `contain`で画像全体を表示。透過画像は淡い市松背景 |
| 壁紙履歴 | 現行の`cover`を維持。拡大では全体を表示 |
| ファイル名 | 最大2行、2行分の高さを確保。全文は拡大画面とアクセシブル名で取得可能 |
| 補助情報 | 解像度・形式。詳細なファイルサイズは拡大画面へ表示 |
| 所属 | 最大2つのグループ名と「ほかN件」。長い名前は1行で省略し、カード高さをグループ数で増やさない。全所属は編集画面で確認 |
| 管理ページの下端 | 「グループ」「削除」。画像自体のクリックで拡大 |
| 選択 | 左上のチェックボックスと外枠。画像全体を着色して見えにくくしない |
| 状態 | 読み込み中・未到着／読取待ち・読取失敗を区別。最後の正常画像があれば保持し、状態を併記 |

カードは縦flex、画像枠は非縮小、操作列は`margin-top:auto`を基本とする。ラベルの長短、読取状態、所属数が違っても同じ行の操作列を揃える。カード全体をbuttonにせず、画像・チェック・操作ボタンが入れ子のインタラクティブ要素にならない構造にする。

画像が読み取れないカードも所属編集は可能とする。拡大や画像選択の可否は用途側で決める。画像選択では、既存の未到着参照を維持できる現行契約を壊さない。

## 5. 画像サイズの変更

### 5.1 操作と値

「画像サイズ」のラベルと「小」「大」を持つnative rangeを使う。設定画面へ移動せず、ポインター操作とキーボードの両方で変更できる。

- 初期値は基準カード幅260 CSS px。範囲180～360、刻み20を初期実装値とする。最終的な見た目の確認で調整した場合は本書と部品の既定値・試験を同時に更新する。
- 数値はカードの基準幅であり、原画像のピクセル数やサムネイル生成設定ではない。画面には「小〜大」を示し、アクセシブルな値説明にも大小と標準位置を含める。
- 左右矢印で1段階、Home/Endで最小・最大。ドラッグ中は即時反映し、数値入力欄・保存ボタン・保存のたびの通知は置かない。
- 列は`repeat(auto-fill, minmax(min(100%, 基準幅), 1fr))`を基本とし、利用可能幅へ均等に広げる。実カード幅は列数と本文幅で変わる。グループ列や検索欄の文字まで縮小しない。
- 列数変更時の大きな移動アニメーションは付けない。画像枠、ファイル名、補助情報、操作列の順序を保つ。
- ライブラリー・選択ダイアログ・壁紙履歴の3か所に同じ操作を提供する。初期値は揃え、保存値は独立させる。

### 5.2 選択・閲覧位置の保持

リサイズ開始前に、一覧の上端に見えている画像の安定キーとスクロール領域上端からの距離を記録する。レイアウト確定後に同じ画像へ位置を合わせる。キーが消えた場合は直後、なければ直前の残存画像へ寄せる。

スライダーのフォーカス、選択集合、検索文字列、選択グループ、読み込み済み件数は維持する。画像DOMを全破棄して先頭へ戻す処理や、幅の変更のたびに画像を再登録する処理は行わない。ホイールやタッチで利用者がスクロールした場合は、その操作を優先する。

### 5.3 保存

| 対象 | 保存先・責務 |
| --- | --- |
| 管理ページと本体の選択ダイアログ | 新設する本体`GalleryViewStateStore`。配置別PC専用rootの`image-gallery-state.json` |
| WallpaperSlideshow | 既存のホストStorage APIを利用。Applet専用キー`gallery.history`。manifestへ`storage` capabilityを追加 |
| グループ・画像参照 | 従来の`settings.json`内`imageLibrary.groups` |
| 原画像 | 注入された共有assets root内の既存images領域 |

本体ファイルの予定形式:

```json
{
  "schemaVersion": 1,
  "library": { "cardWidth": 260 },
  "picker": { "cardWidth": 260 }
}
```

保存できる値は検証済みのcardWidthだけ。未指定の画面は既定値を使い、初期表示だけでファイルを作らない。保存はchange／ポインター解放、キー操作終了を契機にまとめ、ドラッグの各フレームでは書かない。アダプターは送信を直列化し、処理中に変更された値は最後の値だけを次に送る。

サイズ保存に失敗しても現在の表示は維持する。「表示サイズを保存できませんでした」の説明と明示的な再試行を用意し、保存成功と報告しない。破損・未知版は元ファイルを上書きせず、セッション内では既定値から調整可能とする。新規ファイルは原子的に書き、兄弟の画面の値を失わない。

Shell提供元の変更で値を失わないよう、本体の値をShellのlocalStorageへ置かない。壁紙履歴もHTMLのパスに依存せず、既存の.NET `Storage.GetAsync/SetAsync`と宣言済みpageActions経由で読み書きする。カードサイズを共有設定や壁紙の`thumbnailWidth/thumbnailHeight`へ書き戻さない。

検索・選択グループ・選択集合・スクロール位置は本体Window内のページ表示状態として保持し、再起動をまたいで保存しない。通常のページ往復とShellの復旧では復元する。選択ダイアログは呼出ごとに現在の参照から開始し、前回の別の選択操作を引き継がない。

## 6. 画像追加とグループの操作

### 6.1 画像を追加

1. 「画像を追加」で既存のネイティブファイル選択を開く。複数選択を許可し、選択開始時の対象グループIDを記録する。
2. 各ファイルを現行の形式・容量・寸法・同名検査で登録する。原画像は再圧縮せず、同名同内容は再利用、同名別内容は拒否する。512件上限に達した後のファイルも黙って省かず、個別の失敗結果を返す。同内容の再利用は新規件数に含めない。
3. 通常グループから開いた場合は登録成功／再利用した画像をそのグループへ追加する。「すべて」「未分類」からの追加では所属を作らない。既存画像を再利用したときの他の所属は維持する。
4. 全体結果として、追加・再利用・失敗と、グループ追加の成否を区別して画面へ返す。成功した原画像を失敗分の巻き戻しで削除しない。
5. 成功画像を選択し、検索を解除して最初の成功画像の位置へ移動する。表示件数を増やす必要があればその画像まで表示する。未分類から既存の分類済み画像を再利用した場合等、成功画像が現在の一覧に含まれなければ「すべて」へ切り替える。グループが消失した場合も「すべて」へ戻し、所属追加の失敗を示す。

原画像の登録とグループ設定の保存は別の確定操作であり、1つの原子的トランザクションとは扱わない。登録後の所属保存に失敗した場合は原画像を保持し、必要なら「グループへの追加を再試行」だけを実行できるようにする。登録を自動再送しない。

入力時の不正ファイルや重複はファイル別に示す。処理中も操作列の高さを変えず、件数の進捗は予約した状態領域とaria-liveで伝える。登録処理は本体の機能側が所有し、ページを離れても受付済みの処理を二重起動しない。同じWindowで戻った場合は処理中／結果を取得できる。終了後の自動再開は追加しない。

### 6.2 単一画像の所属

「グループ」で「所属グループを編集」を開き、画像名と全グループのチェックを表示する。初期値は現在の所属。「適用」でこの画像の所属集合だけを保存し、「キャンセル」で破棄する。グループ0件のときはその旨と「グループを追加」への導線を示す。

### 6.3 複数選択

- チェックボックスで選択する。画像クリックは拡大であり、選択の切替を兼ねない。
- 1件以上選択すると一覧上に「N枚を選択」「グループに追加」「選択を解除」を出す。通常グループ内では「このグループから外す」も出す。
- 「すべて選択」は現在のフィルターに一致する全件を対象とし、未表示の後続64件も含む。「検索結果をすべて選択（N枚）」等、範囲を明記する。
- 「グループに追加」は選んだグループへの所属を加えるだけで、各画像の他の所属を置換しない。「このグループから外す」は当該所属だけを除き、画像は残す。
- 一括解除は対象グループ名と枚数を確認してから適用する。単一編集で全チェックを外した場合も原画像は残る。
- フィルター変更では選択を解除する。データ更新でフィルター対象から外れた画像だけを選択から除外し、残りを保つ。

複数画像の所属変更は、UIから既存の単一操作を連続送信する方式にしない。本体の編集サービスへ一括操作を追加し、対象画像ごとの直前所属、対象グループの生存、各上限を全件検査した後に1回の設定保存で確定する。1件でも競合すれば全件未適用とし、選択を保持して再取得を促す。無関係な画像や設定への同時変更は保持する。

一括操作は追加／解除するグループID、画像参照の集合、画像ごとの直前所属を受ける限定契約とし、全設定を受け取らない。最大512画像・既存の所属上限・JSONのサイズ上限を送受信両側で検証する。既存のNode/.NET登録・選択APIへ、この管理用操作を自動公開しない。

### 6.4 グループの管理

| 操作 | UIと保存 |
| --- | --- |
| 追加 | 左の「グループを追加」→名前のダイアログ→「追加」。成功後、そのグループを選択 |
| 名前変更 | グループ行の「…」→「名前を変更」→「適用」。ID・画像参照は維持 |
| 削除 | グループ行の「…」→「グループを削除」。名前と「画像と使用先は残ります」を確認して削除 |
| 並べ替え | グループ見出しの「…」→「並べ替え」。既存の共通並べ替えダイアログで確定 |

「すべて」「未分類」は名前変更・削除・並べ替えの対象外。通常グループの内部IDで区別し、表示名だけで仮想一覧と判定しない。現在選択中のグループが削除されたときは「すべて」へ戻す。名前のtrim・空白・重複・80文字・64グループ上限、直前値を使った競合検査を維持する。

名前の一時入力はダイアログ内に置き、共通入力のblur/Enter確定・Escape取消・IMEの規則を適用する。ページ全体の保存／破棄、共有ドラフト、未保存通知は追加しない。

## 7. 拡大・画像選択・壁紙履歴

### 7.1 拡大プレビュー

管理ページの画像クリックと「拡大」で同じプレビューを開く。画像は全体表示、透過背景を維持し、ファイル名・寸法・形式・容量・全所属を確認できる。閉じるボタンとEscapeで元の画像ボタンへフォーカスを戻す。プレビューを開いただけで選択集合や所属は変更しない。

共通化するのはプレビュー画像の表示・読み込み・エラー・補助情報であり、モーダルの所有と表示寿命は利用先のアダプターが担う。ピッカー内の拡大を閉じたときに、親の画像選択まで確定・取消しない。

### 7.2 画像選択ダイアログ

- 共通カードを単一選択モードで使う。画像クリック／Enter／Spaceは候補選択、別の「拡大」はプレビューとし、管理モードと区別する。
- フッターの「画像を使う」「キャンセル」、未選択時の確定禁止を維持。ダブルクリックによる暗黙の確定は追加しない。
- グループ選択と検索、画像追加、画像サイズを提供する。グループ管理や複数選択の一括操作は出さない。
- 画像追加は独立した登録であり、選択や親編集を取り消しても原画像が残る契約を維持する。
- 「画像を外す」は元の画像入力欄だけに置く。プレビュー自体が選択ボタンである0.73.9の入力UIを保持する。
- 本体の選択、Appletからの`registeredImages.pick`は同じ選択画面を使う。返す型や取消・フォーカス復帰の契約を変更しない。

### 7.3 WallpaperSlideshow

共通カード・サイズスライダー・拡大表示を使い、モニター切替、ページング、履歴順、日時等の表示モデル、「開く」「削除」をApplet側に残す。ライブラリーのグループ一覧・画像登録・複数選択は表示しない。

履歴項目の識別は`generation + slot`を維持し、元ファイル名や表示順を操作キーへ流用しない。`history.delete-request/confirm/cancel`の確認トークン、処理中の二重操作防止、世代別の画像登録と解放を保持する。共通ギャラリーへ元ファイルの削除処理を実装しない。

サイズの読取／保存には自身のpageActionsを追加し、ホストStorageの専用キーへ接続する。既存の`thumbnailWidth/thumbnailHeight`・履歴件数・1ページの件数・ファイル名の表示設定は保持し、カードを大きくしただけでこれらを書き換えない。履歴の生成画像の解像度は現設定に従うため、低い設定値の場合に拡大表示の画質を過大に保証しない。

## 8. 共通部品と接続の境界

### 8.1 フレームワークに依存しない表示部品

正本は本体repoに新設する公開UI部品`ui/image-gallery/`とする。DOMを生成するTypeScriptとスコープ付きCSSで実装し、React、Electron、.NET、`window.dock`、`window.appletPage`へ直接依存させない。

予定する入口は`mountImageGallery(container, options)`、更新は`setModel(model)`、終了は`dispose()`。Reactでは薄いラッパーでmount／更新／解放し、通常HTMLでは同じ部品を直接使用する。CSSのルートとクラスを名前空間化し、body・button等のグローバル規則を上書きしない。

| 共通部品の入力・出力 | 内容 |
| --- | --- |
| 項目モデル | 安定キー、表示名、補助情報、ラベル、画像状態、選択可否、操作IDと表示名 |
| 表示条件 | テーマ、基準幅、contain／cover、単一／複数／選択なし |
| 利用者の操作 | 項目選択、拡大要求、操作IDの実行要求、サイズ変更・確定 |
| 画像供給 | 利用先のアダプターが、項目キーと必要な解像度から承認済みURL等を取得 |
| 寿命 | 項目の差分更新、DOMの安定性、購読・observer・画像参照の解放 |

共通部品はファイルパスの解決、登録、所属保存、画像削除、設定の直書き、コマンドの実行、履歴の監視を行わない。画面固有のグループ列・検索条件・ページングも呼出元が所有する。共通化のために壁紙をライブラリーへ登録したり、履歴ファイルを共有assetsへ移したりしない。

表示名やラベルはテキストとして描画し、入力されたHTMLを挿入しない。画像のready／loading／missing／errorはアダプターの表示状態として扱う。現行の`available`だけでは欠落と読取失敗を区別できないため、本体の内部取得結果を拡張して投影し、既存の公開フィールドの意味は保つ。

### 8.2 配布と更新

同じソースからローカル配布用のJavaScript module・CSS・API版とhashを記したmanifestを生成する。本体とDefault Shellは公開部品をビルド入力として使う。WallpaperSlideshowはその生成物をAppletの`web/vendor/image-gallery/`へ梱包する。

生成元は一か所とし、Applet内の生成物を手編集しない。Appletのビルド／発行は共通部品の生成と版・hashの検査を行い、未生成・不一致では失敗させる。古い生成物へ黙って戻さない。開発時に本体repoの共通ビルド手順を参照しても、配布後のAppletは自分のフォルダー内の資産だけで動くようにする。

実行時のCDN・ネットワーク取得、隣の開発repoのimport、ホスト内部ファイルを読むURL、CSPの緩和は不要な構成にする。共有UI部品のビルドで本体の`out/main`を削除・再生成しない。共通部品更新の公開は、同梱する各モジュールの通常の発行・更新で反映する。

### 8.3 本体ページとShell

- 新設する`ImageLibraryPageSession`が表示モデル・グループ／検索・選択・操作の可否を所有し、`ImageLibraryHost`の保存サービスを利用する。
- `ShellPageRequest/Model/Action`へ`kind: 'image-library'`を追加し、Default Shellに対応する本文を用意する。本体rendererは表示枠を報告し、一覧を二重描画しない。
- `page.image-library`をShell領域カタログ・manifest検証・提供元選択・故障復旧へ追加する。旧Shellが未提供ならこの領域だけDefault Shellへ戻る。
- 表示モデルにはファイル名を**表示名として**明示的に投影する。リボン用のopaque asset契約は維持する。操作と画像取得はページセッション内の不透明IDで行い、表示名や任意の絶対パスを操作入力として信用しない。
- グループ操作・登録・画像取得を内容Controllerへ委譲し、`ShellPageHost`へ画像固有の条件分岐や保存処理を持ち込まない。
- 接続元WebContents、main frame、URL、session、操作の現在の可否を実行直前に検査する。ページ破棄後の要求、古いモデルの画像ID、遅延応答を拒否する。
- 通常のページ往復に必要な状態と登録ジョブはWindowに属する機能セッションへ置く。表示Controllerの破棄でDOM／購読を解放し、非表示ページの描画タイマーを残さない。

### 8.4 ダイアログと背景

グループ追加・名前変更・所属編集・削除確認・並べ替えは、本体rendererの既存共通ダイアログを再利用する。Shellの操作から本体へ依頼し、管理ページのrouteを保ったまま表示する。

現状のHostModalLayerはリボン・タイトルバー・ステータスバーの登録を主に扱い、Shell本文を自動で覆う契約ではない。今回のページViewも、表示希望・capture／hide・入力停止・破棄を共通の背景管理へ接続する。独立した場当たり的な背景や、設定ページへの一時遷移を追加しない。

共通プレビュー内容も同じ本体のモーダル枠へ置く。画像選択からの重なったプレビューでは、最後のモーダルが閉じるまで背景を復帰させない。Shell交代・route変更・Window非表示時は現在の所有者を再検査し、閉じた後に古いViewへフォーカスしない。

既存のAppletからの画像選択が持つcapture／hideと今回のShell本文登録を照合し、同じViewを二重に覆ったり、片方の終了で早く復帰させたりしない。今回の本文登録だけで、すべてのWeb／Applet Viewも自動的に対応したと扱わない。

WallpaperSlideshowのページ内プレビューは、そのHTMLのnative dialogと既存の限定bridgeを使用する。共通画像部品が独自に本体のモーダルAPIを呼ぶ構成にはしない。

## 9. サムネイルと表示の安定性

本体の現行64pxサムネイルと96px円形画像は、小型アイコン用として契約を維持する。ギャラリー用には別の縮小画像を必要時に生成する。512／1024／2048pxの長辺を初期候補とし、実カード幅とdevicePixelRatioから最小の十分な段階を選ぶ。原画像より拡大して生成しない。

- 一覧snapshotに全件の大きなbase64画像を含めない。メタデータと画像取得を分け、表示中と近傍のカードから要求する。
- 生成は非同期・同時数を制限し、同一画像・内容世代・サイズ段階の要求をまとめる。WebPは既存のsandbox化したdecoderの制約を維持する。
- 大きな縮小画像はPC内メモリーの上限付きキャッシュとする。初期の生成画像予算は64MiBを基準に計測し、実画像のdecodeメモリーも含めて確認する。新しい画像インデックスや派生画像の永続フォルダーは作らない。
- ピクセル密度の変化やスライダー操作では段階が変わったときだけ再取得し、解像度の高い正常画像を低い画像へ取り替えない。
- 新しい画像をdecodeできるまで現在の正常画像を残す。読み込みでカード高さ、スクロール位置、操作列を変えない。
- 更新・削除検知で内容世代を変え、古い取得結果で新しい画像を上書きしない。復旧時は元の安定キーで置換する。
- Shellへ配信するURL／不透明IDは許可された生存Viewへ限定する。本体の既存asset配信の送信元検査を再利用または拡張し、リモートWebへ公開しない。
- WallpaperSlideshowは既存のページ画像登録と解放をそのままアダプターへ接続する。共通部品の都合で1MiBのRPC上限を緩めたり、画像bytesをpageActions結果へ埋めたりしない。

## 10. 空状態・失敗・アクセシビリティ

| 状態 | 表示と操作 |
| --- | --- |
| 登録0件 | 「画像がありません」と「画像を追加」 |
| 空の通常グループ | 「このグループには画像がありません」。追加と既存画像の所属変更への案内 |
| 検索0件 | 「該当する画像はありません」と検索解除。グループ自体を消さない |
| データ取得失敗 | 直近の正常一覧を保持し、状態領域に再取得を表示。失敗を空一覧として扱わない |
| 保存競合 | 入力・選択を保持して再取得を促す。自動上書き・自動再送しない |
| 画像単体の読取失敗 | カード内に状態を表示。他の正常画像やグループ操作は使える |

すべての操作をキーボードで実行可能にする。チェック、スライダー、検索、各ボタンはnative要素を用い、クリック可能な画像にも操作名を付ける。ホバーだけで操作を発見させない。

ダイアログの初期フォーカス・囲い込み・復帰、入力中のIME、Escapeの対象を維持する。画像カードに複合した独自の矢印キー操作を新設せず、検索の文字選択・スライダーの矢印・既存ショートカットを奪わない。

保存・登録の最終失敗は[共通エラー報告](error-reporting.md)、処理中や選択件数はaria-liveと画面内の状態領域へ接続する。共有ヒントの表示設定とエラー／状態表示を混同しない。成功のたびのバナーや読み上げは追加しない。

## 11. 実装の順序と変更対象

| 工程 | 主な対象 | 完了条件 |
| --- | --- | --- |
| A. 共通部品 | 本体`ui/image-gallery/`、専用ビルド、型と部品試験 | 3用途のモデルで同じカードを描け、サイズ変更とキー付き更新が独立動作 |
| B. 本体のサービス | 画像縮小取得、一括所属、複数登録結果、GalleryViewStateStore | 保存の競合・部分失敗・原画像保持とサイズ復元を検証 |
| C. 管理ページ | Shell公開型／Controller／Default Shell／navigation／標準リボン／コマンド | 左グループとページ内スライダーを持つページから全管理操作が可能。設定の同名カテゴリは除去 |
| D. 選択とモーダル | RegisteredImagePicker、プレビュー、HostModalLayerの本文登録 | 親編集の確定／取消、重なったモーダル、画像入力の現行形状を維持 |
| E. 壁紙履歴 | Appletのvendor梱包、history表示、Storage、限定pageActions | 現行の履歴・開く・削除・画像解放と、新しいサイズ保存が両立 |
| F. 確認と発行 | 対象回帰、固定EXEの隔離GUI、レビュー、文書 | 受け入れ条件を満たし、変更モジュールだけ版更新・発行 |

A〜Cに続き、画像選択の単一選択と重なったプレビュー、壁紙履歴のvendor梱包・Storage保存を実装した。Fの証拠は実行対象の版・hash・fixture条件と一緒に記録する。共通部品の参照だけを理由に、他のAppletを一括変更・再発行しない。

更新が必要な正本文書は、registered-images、shell-pages／shell領域、applet-pagesの標準リボン、settings-sync、共通UIの利用手順、WallpaperSlideshowのdocs/usage.md／DEVELOPMENT／VERIFICATION。実装完了後に本書の状態と実装到達点を更新する。

新しいShell領域を使う提供元のminimumHostVersionは、実際にその公開契約を提供したホスト版に合わせる。WallpaperSlideshowは利用するStorage／pageActions等の最低版を照合し、UI bundleを共用するという理由だけで根拠のない最低版やSDK更新を設定しない。

本体の新規PC専用保存ファイルは0.74.0、予約済みpicker欄への適用は0.74.1、WallpaperSlideshowのStorageキー追加は0.7.0で導入済み。画面外の画像取得を失効させる補正は保存/API契約を変えず、本体0.74.2 / WallpaperSlideshow 0.7.1へパッチ更新する。

## 12. 受け入れ条件と検証計画

### 外観と操作

- 管理ページが左グループ構成で開き、設定には二重の管理一覧が残らない。標準リボンの既定順・既存保存配置・コマンド・復元が整合する。
- 明／暗、本文幅320／760／1280 CSS px相当、Windows倍率100／150／200%を対象に、横はみ出し・重なり・操作不能を確認する。
- 縦長・横長・正方形・透過・短い／長いファイル名・複数所属・欠落画像を混在させ、16:10枠と同一行の操作列の整列を測る。
- 最小／標準／最大サイズと連続ドラッグ、矢印／Home／Endで列数を確認。選択・先頭可視画像・検索・グループ・読み込み済み件数を保持する。
- サイズ変更で全カードを再生成せず、画像が点滅しない。非表示／再表示・データ更新・Shell復旧後も状態を保持する。
- 画像のクリックとチェック、管理モードと単一選択モードの操作が混線しない。

### 保存と失敗

- 3用途でサイズが独立し、再起動後に復元する。共有settings.jsonと原画像のhashはサイズ変更で変わらない。
- サイズ保存の失敗、破損・未知版、古い非同期応答で、設定／画面状態を壊さず未保存を識別できる。
- 同名同内容／異内容、不正形式、容量／寸法／件数上限、複数登録の部分成功を確認する。所属保存失敗後も成功した原画像を保持する。
- 単一・一括所属、グループ削除／並べ替えの競合を検証。無関係な変更を保持し、一括処理の一部だけを保存しない。
- 512画像、64グループ、4096所属で、件数・検索・全件選択・追加表示・大きな画像の取得量とメモリーを確認する。

### 共通部品・境界・既存回帰

- 本体とAppletの共通bundleの版・hash・同梱を照合し、Appletを開発repoのない隔離配置で起動する。
- ページsession失効、偽の項目ID、任意パス、リモートWebからの操作を拒否する。
- HostModalLayerへ接続した本文とバーを、実際のViewの合成・フォーカス復帰・重なったモーダルで確認する。
- 既存の画像入力、リボン画像／既定アイコン、ProfileとWebAppletの画像参照、Node/.NETの選択・登録APIの互換性を検証する。
- WallpaperSlideshowのgeneration／slot、モニターとページ切替、画像開放、削除の確認／取消、停止・再起動をfixtureで検証する。壁紙描画・Explorer・実ごみ箱の動作確認とは区別する。

既存の`tests/registered-images.test.cjs`、`tests/shell-boundaries.test.cjs`、画像ライブラリー・リボン・ページ・モーダルのGUI、およびWallpaperSlideshowの`test-history-page-ui.cjs`を影響範囲に応じて更新する。共通部品とページController・表示状態保存の試験を追加し、成功した同じ対象の試験は[共通手順](development-workflow.md)に従って再利用する。

本体管理ページと共通部品の検証記録は[VERIFICATION](../VERIFICATION.md)を参照する。上記は全工程の受け入れ計画であり、fixtureとCSS幅での成功を物理Windows倍率・実NAS・壁紙描画の確認済みとは扱わない。
