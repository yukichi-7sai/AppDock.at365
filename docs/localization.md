# 本体の表示言語と翻訳

## 対応範囲

本体の固定文言はi18nextで管理する。設定17ページの本文・選択肢・ヒント・検索カタログ・アクセシブル名と、共通の一覧・編集・並べ替え・確認ダイアログを対応範囲とする。設定値の共有検証、設定ページ操作、設定健全性・Windows起動・Shell提供元・タッチパッド接続、AI/MCP接続設定の保存診断もJSONへ集約する。現在の対応言語は日本語（`ja`）だけとする。

本体の通知センター・ログ・画像ライブラリー、Default Shellの固定文言は未移行。設定からも呼ばれる更新・接続・画像・音声などの共通サービスが返す実行結果やnative確認画面には未移行の文言が残るため、次に所有サービス単位で移行する。API説明・AIへの固定指示文は画面文言と混ぜず、表示翻訳のために動作を変えない。製品名・プロトコル名・単位・識別子はそのまま使う。

Applet設定に使う本体提供の共通操作（追加・編集・削除など）も対象。Applet自身のUI、manifestのタイトル・設定定義・コマンド名・メッセージは対象外。本体側の移行が完了した後にAppletの翻訳契約を別途設計する。

カスタムコマンド名、リボングループ名、ラベルの上書き、接続名、ファイルパス、URL、入力値、Applet提供の名前・本文を翻訳キーとして扱わない。固定文言と同じ文字列や、`language.ja`のようなキーに見える名前でも、入力された文字列を表示する。OS・外部処理のエラー詳細もそのまま差し込み、本体が説明する文章だけを翻訳する。

## 言語設定と保存

- 「表示」→「共通」の先頭に「表示言語」を置き、選択肢は「日本語」だけにする。OSによる自動選択は行わない。
- `host.language`の既定値は`ja`。表示・一般の他項目と同じく`settings-<端末名>.json`の端末専用設定とする。共有設定の同期で別PCの言語を変えない。
- 未指定は`ja`で読み取り、元データを読込時に書き換えない。既定値は既存の省略規則に従うため、保存JSONにキーがなくても正常。`null`、空文字、未対応コードは入力エラーにする。
- フォーム、表示ページの部分JSON、検索、ページリセット、公開設定定義を共通基盤へ接続する。言語専用の保存APIや移行ファイルは作らない。
- ページモデルの`content.language`は、選択中ページの投影とは別に現在の言語を運ぶ。一般やApplet設定を開いても言語コンテキストを失わない。

## リソースと実行経路

正本は`src/shared/locales/ja/host.json`。キーはフラットな意味名（例:`general.files.healthy`）とし、画面名・機能・用途で整理する。文章そのものや連番をキーにしない。i18nextのnamespaceは`host`、`keySeparator: false`でドットをキーの一部として扱う。

`src/shared/i18n.ts`が唯一の初期化入口。リソースを静的importし、同期初期化する。mainのビルドにはJSONとして、rendererにはViteのバンドルとして入り、どちらも発行EXEへ同梱される。実行時ダウンロード、外部翻訳ファイル、起動時のネットワーク待ちはない。JSONの編集を配布物へ反映するには再ビルド・再発行が必要。

Reactは`HostTranslationProvider`と`useHostTranslation()`を使う。Providerは設定画面を包み、portal内のダイアログも同じContextを使う。言語を理由に編集画面をkeyで再生成しない。main/sharedの投影は`getHostTranslator(language)`を使う。`hostText`は現段階で日本語固定のmain診断・静的定義向けであり、将来の動的切替に対応したAPIとはみなさない。

`HostTextKey`は日本語JSONから導出し、存在しないキーを型検査で検出する。列挙IDからのキー生成も型で制限する。文字列の型キャストで任意入力をキーに変換しない。i18nextインスタンス間ではリソースの変更を共有しない。

```tsx
const { t } = useHostTranslation();
return <span>{t('appearance.shell.active', { name: provider.displayName })}</span>;
```

文章全体を一つのキーにし、変数は`{{name}}`など名前付きプレースホルダーで渡す。語順に依存する断片の連結を避ける。変数名を変える場合は全呼出しを同時に修正する。翻訳値と変数は通常のReactテキスト／属性、またはnativeダイアログの文字列に渡す。`escapeValue: false`はReact側のエスケープを前提とし、`dangerouslySetInnerHTML`やHTML連結には使わない。`skipOnVariables: true`により、入力された`{{...}}`や`$t(...)`を再解釈しない。

文章の途中に強調やコード表示を入れる場合は`HostMessage`へReact nodeを渡す。翻訳時には内部の置換マーカーだけを渡し、翻訳後にReact nodeを差し込む。翻訳JSONやユーザー入力をHTMLとして解析しない。文章を組み立てるための助詞・動詞の断片を増やさない。入力方式などの分岐には表示文字列を比較せず、`inputKind`のような安定した識別値を使う。

## 文言変更と試験

キーとプレースホルダーを維持すれば、JSONの値だけを編集できる。保存項目名、コマンドID、ページID、IPCの操作名、JSONの列挙値は翻訳しない。意味が変わる文言変更は、単なる表記修正として扱わない。

操作の試験はページID、設定アンカー、安定したtest ID、保存状態を中心にする。表示文言・アクセシブル名を保証する試験では期待する日本語を明示してよい。その場合は文言変更時に期待値を更新する。すべての期待値を翻訳関数から生成して、誤った翻訳でも通る試験にしない。翻訳抽出を契機に既存の文言検査を無条件で削除しない。

`tests/localization.test.cjs`は、リソースの同梱・同期初期化、変数の無変換、言語値の検証、設定の投影・リセット・端末保存、設定renderer全体と移行済み共有部品への日本語直書き再混入を検査する。`scripts/settings-hints-ui-test.cjs --localization-only`は隔離した画面で先頭配置・日本語だけの選択肢・入力保存・JSON検証・検索・ヒント・設定17ページの明暗と狭幅・カスタム名・強調を含む確認文の無変換を確認する。発行EXEの引数も指定できる。これらは外部AI/MCP/TTSサービスの疎通やWindows設定変更の実機証明ではない。

## 今後の進め方

1. 本体のページ／機能単位で固定文言の所有元を確認し、本文、選択肢、アクセシブル名、ヒント、検索語、エラーをまとめて移行する。未移行範囲をこの文書で更新する。
2. データから来た名前を辞書へ登録せず、既定ラベルとユーザーの上書きを区別する。既存の保存値を翻訳済みラベルへ変換しない。
3. 複数言語を追加する前に、mainの`hostText`、静的コマンド定義、キャッシュした診断本文を、現在の言語を使う投影またはキー＋引数の表示時変換へ接続する。履歴に残す通知・ログの言語方針も決める。
4. 対応言語を追加するときは、言語一覧、型・パーサー、リソース同梱、選択肢の自言語名、未翻訳キーと変数の一致を更新する。複数Window・Shellを含む反映と、編集中の値・フォーカスの保持を検証する。日本語だけの現在の試験を多言語切替の証明としない。
5. 本体移行が完了してから、Appletによるリソース宣言・フォールバック・配布・互換性・言語通知の契約を協議する。現段階でAppletへ翻訳APIを要求しない。

表示言語と地域形式は別の設定概念とする。数値・日付の表示は将来`Intl.NumberFormat`/`Intl.DateTimeFormat`へ集約し、言語・地域・タイムゾーンの方針を決めてから導入する。今回は日時・小数点・保存値を変更しない。今後「特定の瞬間」を保存する場合はUTCのISO 8601等を使う設計が可能だが、毎日の時刻や日付だけの値までUTCへ一律変換しない。
